Servicios en Laravel: qué son, cuándo usarlos y cuándo no

Resumen: un servicio en Laravel es una clase sin estado que encapsula lógica de negocio y se inyecta donde se necesita. Sirve para que tus controllers se limiten a pedir y devolver, tu lógica quede testeable sin pasar por HTTP, y el mismo código sirva desde la web, la consola y las colas. Pero no todos los controllers merecen un servicio: crearlos sin un motivo claro produce capas vacías que solo complican el código.

En esta guía verás qué son, por qué importan, cómo los crea el contenedor de servicios de Laravel, las reglas prácticas para decidir cuándo crear uno, los errores más comunes y una checklist para el final.

1. Qué es un servicio en Laravel

Un service es una clase PHP, sin estado, que encapsula una porción de lógica de negocio. No sabe de HTTP, no sabe de rutas y no sabe de la base de datos más allá de lo que le inyectes.

La analogía más útil: un controller es el mesero y un service es la cocina. El mesero recibe el pedido y lo lleva; la cocina decide cómo se prepara. Un mesero que cocina termina quemándose, igual que un controller con 300 líneas de reglas.

Tecnicamente, un servicio:

  • Vive normalmente en app/Services/.
  • Se instancia mediante el contenedor de servicios, nunca con new.
  • Recibe sus dependencias por el constructor (inyección de dependencias).
  • No guarda estado entre llamadas: dos peticiones simultáneas no deben poder pisarse.
  • Se puede probar de forma aislada, sin levantar la aplicación.

Se crean con php artisan make:class:

php artisan make:class Services/OrderService

No hay un comando make:service en Laravel, y es a propósito: un servicio es una clase cualquiera. La única diferencia con un make:class es la intención que proyecta en quien lo lee.

2. Por qué importan

2.1 Los controllers dejan de ser cuellos de botella

Un controller que recibe, valida, decide y guarda es difícil de leer y más difícil de probar. Separando la decisión del transporte, cada pieza hace una sola cosa.

// Antes: la lógica vive en el controller
public function store(StoreOrderRequest $request): JsonResponse
{
    $order = Order::create($request->validated());

    if ($order->total() > 1000 && ! $request->user()->hasDiscount()) {
        $order->update(['status' => 'manual_review']);
    }

    foreach ($order->items as $item) {
        Inventory::where('sku', $item->sku)->decrement('stock', $item->quantity);
    }

    return response()->json($order, 201);
}

Ese método tiene validación, reglas de negocio y efectos secundarios. Probar la regla del > 1000 exige armar un request HTTP completo y una base de datos con inventario.

// Después: el controller coordina, el service decide
public function store(StoreOrderRequest $request, OrderService $orders): JsonResponse
{
    $order = $orders->place(
        items: $request->validated('items'),
        customer: $request->user(),
    );

    return response()->json($order, 201);
}

Ahora probar la regla es llamar a un método. Sin HTTP, sin request, sin magia.

2.2 La lógica deja de depender del canal de entrada

Este es el argumento más fuerte a favor de los servicios, y el que casi nunca se menciona. La misma regla de negocio rara vez vive en un solo lugar:

  • Un usuario la dispara desde un formulario web.
  • Un comando de artisan la necesita para un script de migración de datos.
  • Un job encolado la reintenta cuando algo falla.
  • Un test la necesita para verificar el comportamiento.

Si la regla está metida en un controller, para reutilizarla en el comando tendrías que duplicarla o inventar un truco para llamar al controller desde consola. Si está en un servicio, los cuatro la llaman igual.

2.3 Se prueban sin HTTP ni base de datos

Un test de un servicio es una función normal: le das datos, verificas el resultado.

it('revisa manualmente los pedidos que superan los 1000', function () {
    $service = new OrderService(new DiscountPolicy());

    expect($service->requiresReview(total: 1500, hasDiscount: false))->toBeTrue();
});

Ese test corre en milisegundos, no necesita base de datos y nunca se rompe porque cambiaste una ruta. Es la diferencia entre una suite que tarda 3 minutos y una que tarda 4 segundos.

2.4 El dominio queda aislado de Laravel

Un servicio bien escrito solo usa tipos de PHP. Si mañana cambias de framework, ese archivo no se toca. El framework está en el borde (rutas, controllers, jobs); la lógica de negocio está en el centro.

3. Anatomía de un servicio bien escrito

<?php

namespace App\Services;

use App\Contracts\InventoryGateway;
use App\Exceptions\InsufficientStock;
use Throwable;

class OrderService
{
    public function __construct(
        private readonly InventoryGateway $inventory,
    ) {
    }

    /**
     * Coloca un pedido y descuenta el inventario.
     *
     * @param  array<int, array{sku: string, quantity: int}>  $items
     */
    public function place(array $items, Customer $customer): Order
    {
        $this->inventory->reserve($items);

        try {
            return Order::create([
                'customer_id' => $customer->id,
                'items' => $items,
            ]);
        } catch (Throwable $exception) {
            $this->inventory->release($items);

            throw $exception;
        }
    }
}

Cuatro cosas a destacar:

  1. Promoción de propiedades con readonly. El constructor es un constructor real y el objeto es inmutable desde fuera.
  2. Tipos explícitos en todo. La firma es la documentación.
  3. Dependencias por contrato, no por implementación. InventoryGateway es una interfaz: el test injecta un doble, producción injecta el real.
  4. No hay request(), ni response(), ni session(). Nada de lo que aparece aquí depende de que haya una petición HTTP en curso.

Los contratos (interfaces) se crean con php artisan make:interface:

php artisan make:interface Contracts/InventoryGateway

4. El contenedor de servicios

El contenedor de Laravel es el que decide qué objeto inyectar cuando pides una clase.

4.1 Resolución automática

Si el constructor pide clases concretas y ninguna tiene argumentos que el contenedor no pueda resolver, no hay que registrar nada:

public function __construct(private Mailer $mailer, private LoggerInterface $logger)
{
}

// El contenedor los crea solo al resolver OrderService.

Funciona porque las clases del framework tienen tipos en sus constructores, así que el contenedor puede deducir las dependencias recursivamente.

4.2 Contratos: el binding explícito

Cuando dependes de una interfaz, tienes que decirle al contenedor qué implementación usar. Se hace en bootstrap/providers.php o en un service provider:

<?php

namespace App\Providers;

use App\Contracts\InventoryGateway;
use App\Services\HttpInventoryGateway;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->singleton(InventoryGateway::class, HttpInventoryGateway::class);
    }
}

Hay tres formas de registrar, y la diferencia importa:

MétodoInstanciasÚsalo cuando
bind() Una nueva por cada vez que se resuelve El servicio es barato y no guarda estado. Este es el valor por defecto correcto.
singleton() Una sola, compartida en toda la aplicación El servicio es caro de construir (un cliente HTTP, un cliente de AWS) o mantiene una caché.
scoped() Una por ciclo de vida / petición Ligado a la petición: con Swoole, Octane o colas de larga duración, evita fugas entre peticiones.

La trampa clásica: un singleton que acumula estado muta de forma silenciosa. Se escribe, funciona en local con una sola petición, y a las 50 peticiones simultáneas los datos se mezclan. Si el servicio guarda estado, no lo hagas singleton.

4.3 Inyección en el método

Cuando la dependencia solo se usa en un método, se pide ahí y no se guarda:

public function store(StoreOrderRequest $request, OrderService $orders): JsonResponse

Laravel lo inyecta sin que hagas nada. Útil para mantener las dependencias de un controller en la lista visible de argumentos.

4.4 Binding contextual

Cuando una interfaz tiene varias implementaciones y la elección depende de quién la pide:

$this->app->when(OrderService::class)
    ->needs(InventoryGateway::class)
    ->give(SandboxInventoryGateway::class);

5. Cuándo SÍ usar un servicio

Si al menos una de estas es cierta, probablemente lo necesitas:

  1. La lógica la van a usar más de un canal. Web, comando de consola, job de cola, test, o una mezcla. Es la señal más fuerte.
  2. Tiene reglas de negocio con condiciones encadenadas. En cuanto un método pasa de unos pocos if y empieza a leer como un párrafo, extráelo.
  3. Necesitas testearla sin pasar por HTTP. Si el test se vuelve incómodo (request falso, base de datos completa, factorías encadenadas), es señal de que esa lógica debería ser un servicio.
  4. Se va a reutilizar en varios modelos o varias rutas. Si tres controllers necesitan el mismo cálculo, ese cálculo es un servicio.
  5. Es una pieza de infraestructura con dos implementaciones. Si vas a tener una versión real y otra de pruebas (sandbox, fake, cache), necesitas un contrato.
  6. Quiero poder nombrarlo. Si el método necesita un comentario de dos líneas para explicar qué hace, casi siempre es un servicio esperando ser creado.

6. Cuándo NO usar un servicio

Aquí es donde se comete el error más común. Estas son las señales de que has creado un servicio de más:

6.1 Un CRUD disfrazado

// No es un servicio. Es un método de Eloquent con más pasos.
class UserService
{
    public function find(int $id): User
    {
        return User::findOrFail($id);
    }

    public function create(array $data): User
    {
        return User::create($data);
    }
}

Esto no es lógica de negocio: es una capa de indirección. Aquí ya tenías User::findOrFail() y ya tenías validación (Form Request). No ganaste nada.

6.2 El servicio anémico

Si tu servicio no decide nada y solo mueve datos de un sitio a otro, la decisión se quedó en el controller. El nombre del síntoma: la clase se llama algo como DataService, BaseService, AppService o HelperService.

Un buen nombre de servicio describe una intención de negocio: SubscriptionService, PricingService, ReportService. Si el nombre describe un sustantivo genérico, probablemente sobra.

6.3 Un condicional suelto

// Un if no necesita su propia clase
if ($order->total() > 0) {
    $order->update(['status' => 'paid']);
}

6.4 La cadena de envoltorios

// Este service solo llama a otro service. Borralo.
class CreateOrderService
{
    public function __construct(private PlaceOrderService $place) {}

    public function execute(array $data): Order
    {
        return $this->place->handle($data);
    }
}

6.5 La prueba de fuego

Antes de dejar el servicio, hazte esta pregunta:

Si borrara este archivo, ¿el código dejaría de funcionar igual de bien?

  • Si la respuesta es "sí, pero más lento de escribir": probablemente sobra.
  • Si la respuesta es "no, se duplicaría en tres sitios": probablemente hace falta.

7. Los 7 errores más comunes

7.1 Poner HTTP dentro del servicio

Un servicio no debería conocer response()->json() ni request()->input(). Si necesitas distinguir "no encontrado" de "no autorizado", lanza una excepción de dominio (OrderNotFound) y deja que el controller la traduzca a un status HTTP.

Esto tiene un matiz importante en sistemas distribuidos: si el servicio llama a otro por HTTP, conviene encapsular esa llamada en un cliente dedicado con su propia política de tiempos de espera y de clasificación de errores. Así el resto de la aplicación no necesita saber que hay una red de por medio, y "el otro servicio está caído" deja de ser un null ambiguo y pasa a ser una excepción con nombre.

7.2 Inyectar modelos Eloquent por el constructor

// Peligroso: el modelo queda cargado y potencialmente obsoleto.
public function __construct(private Order $order) {}

Los modelos se recargan por identidad: el constructor se ejecuta una vez y ese Order puede quedar desactualizado. Pasa el identificador o el modelo como argumento del método, no del constructor.

7.3 Estado mutable en un singleton

Ver la tabla de arriba. Es el error más caro de diagnosticar porque funciona en local con tráfico bajo y falla en producción.

7.4 Nombrar por estructura en lugar de por intención

UserServiceV2, UserNewService, UserService2: la duplicación se resolvió con sufijos. Si dos servicios se parecen, casi siempre la respuesta es extraer la parte común, no clonar.

7.5 Capturar excepciones y tragárselas

// Nunca. Estás ocultando un fallo real al llamador.
try {
    return $this->inventory->reserve($items);
} catch (Throwable $e) {
    return null;
}

Si necesitas registrar, registra; si necesitas compensar, compensa; si necesitas traducir, traduce. Lo que nunca debes es return null.

7.6 Confundir "servicio" con "helper"

Un helper es una función sin estado, sin dependencias y sin identidad. Si tu servicio no tiene dependencias inyectadas y no representa una intención de negocio, probablemente es una función suelta en app/Support/.

7.7 No testearlo

El servicio es justo la parte más barata de testear de toda tu aplicación. Si tiene lógica de negocio y no tiene tests, es la parte más expuesta.

8. Servicio vs. las demás piezas de Laravel

Cada pieza resuelve un problema distinto. La confusión entre ellas es una de las fuentes más comunes de código sobrediseñado.

PiezaResponsabilidadEjemplo
Form Request Validar y tipar la entrada HTTP. No contiene reglas de negocio. Que title no exceda 255 caracteres
Controller Traducir HTTP a una llamada y la respuesta de vuelta a HTTP. Recibir, delegar, responder 201
Resource Decidir qué se serializa y con qué formato. Ocultar password del JSON
Middleware Cosas transversales que pasan por todas las peticiones. Autenticación, CORS, logs, throttling
Policy Responder "¿este usuario puede hacer esto?" Gate::allows('update', $task)
Event / Listener Reaccionar a algo que ya ocurrió, desacoplado. Enviar un email al cambiar el estado
Job (cola) Trabajo diferible, con reintentos y backoff. Generar un PDF de 200 páginas
Action Una única operación invocable. CloseOrderAction
Service Lógica de negocio reutilizable entre canales. Calcular descuentos y decidir el precio final

La diferencia con un Job: un Job hace algo más tarde. Un Service decide algo ahora. Un Job suele contener un Service, no al revés.

La diferencia con un Action: una Action es un caso de uso puntual y suele tener pocos métodos. Un Service agrupa lógica de negocio relacionada y suele exponer varios métodos. Si tienes una sola operación y no se reutiliza, una Action es más honesto.

9. Ejemplo completo, con interfaz y test

El contrato

<?php

namespace App\Contracts;

interface InventoryGateway
{
    public function reserve(array $items): void;

    public function release(array $items): void;
}

La implementación real

<?php

namespace App\Services;

use App\Contracts\InventoryGateway;
use Illuminate\Support\Facades\Http;

class HttpInventoryGateway implements InventoryGateway
{
    public function reserve(array $items): void
    {
        $response = Http::post(config('services.warehouse.url').'/reservations', ['items' => $items]);

        $response->throw();
    }

    public function release(array $items): void
    {
        Http::post(config('services.warehouse.url').'/reservations/release', ['items' => $items])->throw();
    }
}

El servicio de negocio

<?php

namespace App\Services;

use App\Contracts\InventoryGateway;
use App\Exceptions\InsufficientStock;
use App\Models\Customer;
use App\Models\Order;
use Throwable;

class OrderService
{
    public function __construct(private readonly InventoryGateway $inventory)
    {
    }

    /**
     * @param  array<int, array{sku: string, quantity: int}>  $items
     *
     * @throws InsufficientStock
     */
    public function place(array $items, Customer $customer): Order
    {
        try {
            $this->inventory->reserve($items);
        } catch (Throwable $exception) {
            throw new InsufficientStock(previous: $exception);
        }

        return Order::create([
            'customer_id' => $customer->id,
            'items' => $items,
            'total' => $this->calculateTotal($items),
        ]);
    }

    /**
     * @param  array<int, array{sku: string, quantity: int, price: int}>  $items
     */
    public function calculateTotal(array $items): int
    {
        return array_reduce(
            $items,
            fn (int $carry, array $item): int => $carry + ($item['price'] * $item['quantity']),
            0,
        );
    }
}

El binding

public function register(): void
{
    $this->app->singleton(InventoryGateway::class, HttpInventoryGateway::class);
}

El test

<?php

use App\Exceptions\InsufficientStock;
use App\Models\Customer;
use App\Services\OrderService;

it('crea un pedido y reserva el inventario', function () {
    $gateway = Mockery::mock(InventoryGateway::class);
    $gateway->shouldReceive('reserve')->once()->with([
        ['sku' => 'ABC-1', 'quantity' => 2, 'price' => 500],
    ]);

    $order = (new OrderService($gateway))->place(
        items: [['sku' => 'ABC-1', 'quantity' => 2, 'price' => 500]],
        customer: Customer::factory()->create(),
    );

    expect($order->total)->toBe(1000);
});

it('traduce un fallo de inventario a una excepcion de dominio', function () {
    $gateway = Mockery::mock(InventoryGateway::class);
    $gateway->shouldReceive('reserve')->andThrow(new RuntimeException('timeout'));

    expect(fn () => (new OrderService($gateway))->place([], Customer::factory()->create()))
        ->toThrow(InsufficientStock::class);
});

Ninguno de esos tests toca HTTP, ni rutas, ni el contenedor de servicios. Por eso corren rápido y por eso fallan de forma útil cuando algo se rompe.

10. Checklist antes de crear un servicio

Antes de escribir el archivo, pregúntate:

  • ¿Esta lógica la van a usar más de un canal de entrada?
  • ¿Sabría testearla sin montar una petición HTTP completa?
  • ¿El nombre del servicio describe una intención de negocio, no un sustantivo genérico como "Data" o "Helper"?
  • ¿Tiene más de una razón para cambiar por separado?
  • ¿Puedo explicar su responsabilidad en una frase, sin usar la palabra "y"?

Si respondiste "no" a las dos primeras, probablemente no necesitas un servicio todavía.

Si la respuesta es sí a todas, créalo. Y cuando lo crees, no olvides la parte que más se pasa por alto: pruébalo aislado. Un servicio sin tests es una capa que nadie va a atreverse a tocar.

Nota: los ejemplos usan php artisan make:class Services/... y php artisan make:interface Contracts/..., los comandos disponibles en Laravel 11, 12 y 13. No existe un make:service ni un make:contract: un servicio es una clase normal, y la intención la pone el nombre y la carpeta.
