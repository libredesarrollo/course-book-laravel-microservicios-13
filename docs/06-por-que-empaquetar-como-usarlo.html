Módulos Composer · Frontera entre microservicios

¿Por qué empaquetar y cómo lo usamos?

La idea: no duplicar código, sino empaquetar la frontera. En lugar de copiar clientes HTTP, middlewares, identidades o health checks, los movimos a paquetes Composer locales para que cualquier microservicio los consuma sin escribir código de integración.

¿Por qué empaquetar?

Evitar duplicación, mantener contrato único y desacoplar responsabilidades.

Una sola fuente de verdad

El cliente HTTP, el middleware que autentica, la identidad y el ciclo de vida de sesión viven en un solo sitio. Si cambia el contrato con user-service, solo se toca el paquete.

Frontera completa

No solo cómo llamar, sino cómo integrar. El paquete trae el middleware, el value object de identidad y el helper de sesión para que la app solo decida rutas, vistas y redirecciones.

Sin acoplamiento a implementación

Los consumidores inyectan el contrato IdentityProvider, no la clase UserServiceClient. Se puede cambiar el transporte sin tocar controllers.

Consistencia transversal

request.id, log.context y health se comportan igual en todos los microservicios. El paquete ofrece los bloques, la app decide dónde los monta.

Paquetes que usamos

Dos paquetes locales, instalados con type: path.

demo/microservices-user-service-client

IdentityProvider + UserServiceClient

Contrato HTTP hacia user-service. authenticate() devuelve null si el token es inválido (401).

AuthenticateWithUserService

Middleware registrado como alias auth.user-service. Valida por HTTP, limpia sesión si es inválida y deja la identidad en atributos.

AuthenticatedUser + TokenSession

Identidad tipada (fromRequest()) y ciclo de vida de sesión web respaldada por token remoto (emisión + revocación con mejor esfuerzo).

demo/microservices-observability

EnsureRequestId

Genera/respeta X-Request-Id, lo guarda en atributos y lo devuelve en la respuesta.

AttachLogContext

Añade request_id, service, ip, method, path al contexto de logs.

HealthController

Respuesta JSON idéntica en todos los servicios. La ruta la decide la app.

¿Cómo lo usamos?

Cuatro pasos: instalar, configurar, enganchar y proteger.

1) composer.json

{
  "repositories": [
    { "type": "path", "url": "../packages/microservices-observability" },
    { "type": "path", "url": "../packages/microservices-user-service-client" }
  ],
  "require": {
    "demo/microservices-observability": "@dev",
    "demo/microservices-user-service-client": "@dev"
  }
}

2) .env

APP_NAME="Billing Service"
USER_SERVICE_URL=http://127.0.0.1:8000
USER_SERVICE_TIMEOUT=3
USER_SERVICE_CLIENT=billing
# Para API pura: dejar vacío para siempre responder 401 JSON
USER_SERVICE_SSO_START_ROUTE=

3) bootstrap/app.php

use Illuminate\Foundation\Configuration\Middleware;

->withRouting(
    web: __DIR__.'/../routes/web.php',
    api: __DIR__.'/../routes/api.php',
    health: '/up',
)
->withMiddleware(function (Middleware $middleware): void {
    $middleware->appendToGroup('api', 'request.id');
    $middleware->appendToGroup('api', 'log.context');
})

4) rutas + controller

use Demo\Microservices\Observability\Http\Controllers\HealthController;
use Demo\Microservices\UserServiceClient\AuthenticatedUser;

Route::get('/health', [HealthController::class, 'index']);

Route::middleware('auth.user-service')->group(function () {
    Route::get('/invoices', [InvoiceController::class, 'index']);
});

// En el controller
$user = AuthenticatedUser::fromRequest($request);
// ... usar $user->id, $user->name, $user->email

Prueba real: billing-service

Nuevo microservicio creado desde cero, sin escribir cliente HTTP.

Flujo

Sin token

GET /api/invoices → 401 con mensaje claro

Token falso

El middleware pregunta al user-service, recibe null → 401

Token válido

Se emite en user-service, el billing-service lo valida por HTTP, deja la identidad y responde con datos del usuario + facturas.

Trazabilidad

Se propaga X-Request-Id y aparece en los logs de ambos servicios.

Respuesta real

curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8002/api/invoices

{
  "user": {
    "id": 1,
    "name": "Ana Torres",
    "email": "ana.torres@example.com"
  },
  "invoices": [
    {"id": 1, "amount": 99.99, "status": "paid"},
    {"id": 2, "amount": 49.5, "status": "pending"}
  ]
}

Hecho: Nuevo microservicio, cero líneas de cliente HTTP escritas. Solo rutas, configuración y uso del paquete.

Reglas de diseño que seguimos

Lo que sí empaquetamos vs lo que no.

Sí va al paquete

Lo idéntico entre servicios: observabilidad, cliente HTTP, middleware que valida, identidad, sesión con token remoto, health check.

No va al paquete

Lo específico: vistas, redirecciones, validaciones, reglas de negocio, lógica de emitir tokens (solo existe en user-service).

La app decide, el paquete ofrece

Aliases se registran solo si no existen. Rutas, grupos de middleware y sso_start_route los decide la aplicación.

Contratos primero

Inyectar IdentityProvider, no implementación. 401 → null, errores de red/infra → excepciones con semántica distinta.

Verificación

Todo validado.

Tests

Calidad

Pint en servicios y en packages/ (ahora sí se formatea). HTML de docs válido, sin estilos inline, sin recursos externos, sin CJK.

E2E

Health idéntico, login web, logout con revocación en peer, API sin token 401, y trazabilidad X-Request-Id cruzada.

Propuesta 3

billing-service funciona: consume el paquete sin escribir cliente HTTP. Autentica, identifica y responde con datos del usuario validado.
