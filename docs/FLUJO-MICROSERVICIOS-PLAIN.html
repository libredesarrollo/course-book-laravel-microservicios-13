Sistema de Tareas Inteligente

Comunicación síncrona por HTTP entre dos microservicios Laravel independientes, con autenticación delegada — y hacia dónde va desde aquí.

┌─────────────┐     ┌────────────────────────────────┐     ┌──────────────────────────┐
│             │     │                                │     │                          │
│  Cliente    │────▶│  task-service   :8001          │────▶│  user-service  :8000    │
│  curl /     │     │  db_tasks.sqlite               │ GET │  db_users.sqlite         │
│  Postman/UI │◀────│  API REST + UI web             │◀────│  /api/tokens  /api/user  │
│             │201  │  NO tiene tabla users          │200  │  (identidad)  headless   │
└─────────────┘     └────────────────────────────────┘     └──────────────────────────┘

Para saber quién llama, el task-service no tiene usuarios: le reenvía el token al user-service por HTTP y pregunta. Si ese servicio responde 200, sigue; si dice 401, el token no vale; si está caído, devuelve 503 y nadie puede autenticarse.

Cómo leer este documento: secciones 1 a 12 = lo que está implementado y verificado hoy. Secciones 13 a 21 = qué sigue después, no implementado, es una hoja de ruta con el razonamiento detrás de cada decisión.

tasks.user_id es un unsignedBigInteger indexado pero SIN llave foránea, a propósito: una FK física exigiría que ambas tablas vivieran en el mismo motor de base de datos, que es exactamente lo que rompe el aislamiento.

En cambio api_tokens.user_id SÍ tiene llave foránea, porque es una integridad interna del user-service con su propia tabla. Lo que no existe son FKs cruzadas.

2. El flujo completo, paso a paso

2.1 Login (una vez)

  1. El cliente manda email y contraseña a POST /api/tokens del user-service.
  2. El user-service verifica el hash de la contraseña y emite un token opaco: 64 caracteres hexadecimales aleatorios. En su tabla guarda solo el SHA-256.
  3. Devuelve 201 con el token en claro. Es la única vez que existe en esa forma.

2.2 Cada request posterior

  1. El cliente envía Authorization: Bearer <token> (API), o el task-service lo lee de su sesión (web).
  2. El middleware AuthenticateWithUserService reenvía el token al user-service: GET /api/user.
  3. El user-service busca por hash y responde 200 con {id, name, email}, o 401 si no vale.
  4. El task-service guarda esa identidad en la petición y continúa.
  5. El user_id sale de la identidad, nunca del cuerpo del request.
  6. Para una tarea concreta, findOwnedTask() comprueba que el user_id guardado sea el del usuario en sesión. Si no, 403.

2.3 El detalle que cambia todo

Ya no existe la validación explícita de user_id. Antes el controller llamaba al user-service para preguntar "¿este id corresponde a alguien?". Ahora esa pregunta ya la contestó el middleware, con el mismo HTTP, en el mismo request. Preguntarlo otra vez sería pagar la latencia otra vez para obtener la misma respuesta.

Es la diferencia entre validar que un dato existe y autenticar quién eres. La segunda absorbe a la primera, y además responde a una pregunta que la primera nunca hizo.

Rutas

GET /api/user — el endpoint clave

Es el que el task-service consulta en cada request. Su equivalente en un proveedor de identidad real es la introspección de tokens: el recurso protegido no guarda usuarios, reenvía el token y pregunta.

GET /api/user
Authorization: Bearer 64-char-token

200  {"id":1,"name":"Ana Torres","email":"ana.torres@example.com"}
401  {"error":"Unauthenticated.","message":"Falta un token válido..."}

Tabla api_tokens

Schema::create('api_tokens', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();

    // Solo se guarda el hash. El token en claro existe una sola vez,
    // en la respuesta del POST /api/tokens.
    $table->string('token_hash', 64)->unique();

    $table->string('name')->default('api-token');
    $table->timestamp('last_used_at')->nullable();
    $table->timestamp('expires_at')->nullable();
    $table->timestamps();
});

Por qué SHA-256 y no bcrypt/Argon2: el token no es una contraseña que alguien pueda escoger, son 32 bytes de random_bytes. No hay espacio de búsqueda que recorrer, así que el atacante tendría que adivinar el token entero. El hash está ahí para que una fuga de la base de datos no sirva. Con una contraseña elegida por el usuario el ataque de fuerza bruta sí es realista, y ahí sí toca Argon2.

Otras decisiones del login

  • Mismo mensaje y mismo status para "usuario inexistente" y "contraseña incorrecta". Si no, la respuesta sirve para enumerar qué emails están dados de alta.
  • last_used_at se actualiza en cada request, para poder listar sesiones activas.
  • El logout revoca la fila. Si solo se borrara la cookie de sesión, el token seguiría sirviendo desde curl hasta que expirara. Eso es un fallo de seguridad, no una molestia.

4. task-service — API REST + UI web

4.1 UserServiceClient: toda la frontera de red

<?php

class UserServiceClient
{
    /** null si el token no es válido */
    public function authenticate(string $token): ?array;      // GET    /api/user
    public function issueToken(array $credentials): string;  // POST   /api/tokens
    public function revokeToken(string $token): void;        // DELETE /api/tokens

    private function send(callable $callback): Response;    // ConnectionException -> excepción
}

Es el patrón de un API Gateway / service client: encapsular la frontera de red para que el resto de la aplicación trate al otro microservicio como si fuera una función local.

La distinción que importa: 401 no es un fallo del servicio, es "este token no vale" y se traduce a null. Cualquier otro status es un problema del peer y lanza excepción. Confundir los dos convierte un "vuelve a iniciar sesión" en un "el sistema está roto".

4.2 AuthenticateWithUserService: el middleware

public function handle(Request $request, Closure $next): Response
{
    $token = $request->bearerToken()
        ?? ($request->hasSession() ? $request->session()->get('api_token') : null);

    if (! is_string($token) || $token === '') {
        return $this->reject($request);
    }

    $user = $this->users->authenticate($token);

    if ($user === null) {
        if ($request->hasSession()) {
            $request->session()->forget('api_token');
        }

        return $this->reject($request);
    }

    $request->attributes->set('authenticated_user', AuthenticatedUser::fromArray($user));

    return $next($request);
}

Una sola pieza decide 401 en JSON para la API y redirección a /login para la UI. Ningún controller tiene que acordarse.

4.3 Identidad y propiedad

// app/Http/Controllers/Controller.php
protected function user(): AuthenticatedUser          // la identidad resuelta
protected function owns(int $userId): bool
protected function findOwnedTask(int $taskId): Task   // findOrFail + abort_unless(owns, 403)

Por qué no route model binding. SubstituteBindings corre antes del middleware de autenticación. Con binding implícito, un anónimo recibía 404 para "esta tarea no existe" y 403 para "existe pero no es tuya": dos respuestas distintas para dos datos que no debería conocer. Resolviéndolo después de autenticar, un intruso solo ve siempre 401.

10. La prueba que demuestra que es un sistema distribuido

Detén el user-service (Ctrl+C) y manda GET /api/tasks con un token válido. El task-service responde 503. Ninguna cantidad de código dentro del task-service pudo evitarlo: la identidad no está en su proceso, está en otro proceso, detrás de otra base de datos, al otro lado de un socket.

En la UI se ve igual de claro: /tasks deja de funcionar y muestra una página que explica que lo que falta es el otro servicio, no esta aplicación.

Y a la inversa: borra user-service/ completo y el task-service sigue funcionando para listar, editar y borrar tareas. Solo pierde la creación de tareas nuevas y el inicio de sesión. Esa es la disponibilidad parcial que da la independencia real entre servicios.

11. Decisiones de diseño (y por qué)

  • tasks.user_id sin llave foránea. Una FK física exigiría el mismo motor de base de datos.
  • api_tokens.user_id sí tiene FK. Es integridad interna del user-service con su propia tabla. Lo que no existe son FKs cruzadas.
  • Token opaco con SHA-256, no JWT. Estado de identidad con un único dueño y revocación inmediata. El JWT se justifica cuando hay terceros validando.
  • Toda la frontera de red en UserServiceClient. 401 = null; cualquier otro status = excepción.
  • findOwnedTask() en vez de route model binding. Evita la fuga 404/403 y centraliza el chequeo de propiedad.
  • Sin selector de usuario en el formulario. Con auth, la tarea es de quien la crea.
  • Cero paso de build. CSS inline en el layout, sin @vite. El proyecto no tiene node_modules, así que con Vite las páginas darían "Unable to locate file in Vite manifest".
  • Validación explícita de user_id por HTTP — eliminada. El middleware ya la hizo.

12. Limitaciones honestas

  • Un salto de red en cada request autenticado. La latencia se suma a la de la base de datos.
  • Sin circuit breaker. Con el user-service caído, cada request espera los 3 s del timeout.
  • La disponibilidad del task-service depende de la del user-service. Si este cae, nadie puede autenticarse.
  • Los tokens no expiran por defecto. La columna expires_at existe y el código la respeta, pero no hay TTL configurado.
  • Sin refresh tokens. Hay que pedir uno nuevo con la contraseña cuando caduque.
  • Sin rate limiting en la emisión. El login de la UI tiene throttle:6,1, pero POST /api/tokens del user-service NO lo tiene. Es el endpoint que recibe contraseñas: el primero que debería estar limitado.
  • Una sola identidad. No hay roles ni permisos; solo "es tuya o no es tuya".
  • Acoplamiento al contrato. Si el user-service cambia la forma del 401, el task-service se entera al instante.

PARTE 2 — Qué sigue después

Nada de esta sección está implementado. Es una hoja de ruta con el razonamiento detrás de cada decisión.

13. Por qué dejamos Lumen atrás

Lumen fue el framework "ligero" de Laravel para microservicios. Laravel dejó de recomendarlo para proyectos nuevos en 2021, y así lo dice la documentación oficial:

"In the years since releasing Lumen, PHP has made a variety of wonderful performance improvements. For this reason, along with the availability of Laravel Octane, we no longer support beginning new projects with Lumen. Instead, we recommend always beginning new projects with Laravel."

— lumen.laravel.com

La última versión estable es v11.2.0 de noviembre de 2024. Lumen solo sigue vivo powering Laravel Vapor.

Las tres razones por las que Lumen perdió

  1. Laravel alcanzó en rendimiento. Route caching, OPcache y la gestión de middleware cerraron la brecha. Lumen llegó a ser "casi igual de rápido" y bastante más incómodo.
  2. No tenía Sanctum, ni Passport, ni Blade. Para una API de microservicio terminabas reinyectando a mano los componentes de Laravel, que es Lumen dejando de ser Lumen.
  3. Octane resolvió el problema para el que Lumen existía, pero sin renunciar a nada.

Consecuencia práctica: el argumento "es un microservicio, entonces Lumen" ya no se sostiene. La velocidad se compra con Octane, no con otro framework.

14. De síncrono a asíncrono: RabbitMQ

Hoy cada request a task-service suma la latencia de user-service:

Cliente ──5ms──▶ task-service ──5ms──▶ user-service
       ◀────────        ◀────────
              Total ≈ 15 ms

RabbitMQ (el driver es vladimir-yuldashev/laravel-queue-rabbitmq, v15, compatible con Laravel 13) movería la parte no urgente fuera del camino crítico.

Detalle que se olvida: ese paquete soporta Octane desde la 13.3, pero exige declarar la conexión rabbitmq en el warm de config/octane.php.

La pregunta que decide: ¿es aceptable que exista una tarea sin usuario válido? Para notificaciones, no hay duda. Para integridad crítica, el saga con compensación es el camino.

15. JWT, Sanctum y mTLS: cuándo cada uno

  • Sanctum (lo que trae Laravel): tokens opacos en base de datos, revocables, con abilities. Perfecto para SPAs y móviles. No para servicio-a-servicio: el user-service tendría que consultar su tabla en cada request.
  • JWT (php-open-source-saver/jwt-auth, el fork mantenido de tymon/jwt-auth): stateless, sin salto de red. Pero revocar es un problema (hasta exp vale), el payload no es secreto, y el skew de reloj rompe nbf/exp. Si ya tienes base de datos, JWT no te compra nada.
  • mTLS o API Gateway: la respuesta de producción. Separa la identidad del servicio de la del usuario, y elimina el salto por request.

El orden sensato es el que permite ver el problema primero. Montar mTLS antes de tener dos servicios es pagar una factura que todavía no te llegó.

16. Laravel Octane

php artisan serve bootea Laravel entero en cada request. Octane (FrankenPHP, Swoole, OpenSwoole o RoadRunner) lo deja residente en memoria.

composer require laravel/octane
php artisan octane:install --server=frankenphp
php artisan octane:start --workers=8
php artisan octane:reload     # tras un deploy, sin downtime

Cuándo NO: por debajo de ~500 requests/minuto la diferencia entre PHP-FPM y Octane es imperceptible. Una API que recibe 50 req/min no tiene un problema de rendimiento; tiene un problema de diseño.

Los riesgos: el estado vive entre requests (un static o un singleton con estado se comparte entre usuarios del worker), el container no se reinicializa, y los logs se acumulan en memoria.

En este proyecto no lo justifica todavía. Lo justificaría si el listado resolviera N llamadas de golpe.

17. Observabilidad

  • Correlación de requests: un X-Request-Id generado en el borde y propagado a cada llamada saliente. Con eso, un grep en los logs de los dos servicios te arma la historia completa.
  • OpenTelemetry para trazas distribuidas: una petición se convierte en un árbol de spans que cruza el límite de los servicios.
  • Logs estructurados en JSON, con user_id, task_id, status, duration.
  • Métricas: p95 de latencia y, sobre todo, cuántas veces falla la autenticación. Esa última es la que te avisa de que necesitas el circuit breaker.

18. Resiliencia: circuit breaker e idempotencia

Circuit breaker. Hoy, con el user-service caído, cada request espera 3 s. Con 50 usuarios son 50 hilos bloqueados. Un breaker memoriza el fallo: tras N errores seguidos deja de llamar y falla de inmediato. De 3 s a 3 ms.

Idempotencia. POST /api/tokens no lo es: si el cliente no recibe la respuesta y reintenta, crea un token de más. Con Idempotency-Key guardado junto a la respuesta, el reintento devuelve la misma.

19. Un tercer servicio: qué se comparte y qué no

Con un tags-service al lado, la pregunta natural es si hay que duplicar el AuthController. La respuesta corta: el middleware sí se mantiene idéntico; el controller no debería compartirse todavía.

Y hay una tentación posterior: meter todo en una carpeta o paquete compartido. La guía:

  • Comparte el vocabulario: el DTO AuthenticatedUser, el concepto de propiedad, el contrato de errores 503/502. No contienen decisiones de arquitectura.
  • Compón las decisiones: "para validar quién es, hay que llamar por HTTP al user-service" es una decisión, y algún día quizá sea JWT o un gateway. Heredarla te impediría cambiar en un solo servicio.
  • Regla de tres: no extraigas hasta la tercera copia.

El detalle completo está en flujo-autenticacion.html, secciones 14 y 15.

20. Despliegue en contenedores

  1. depends_on no espera disponibilidad, solo arranque. Por eso existen los health checks.
  2. USER_SERVICE_URL no puede ser localhost dentro de un contenedor: ahí solo está él mismo.
  3. Un contenedor no debe escribir en el sistema de archivos. storage/framework/* como volúmenes compartidos.
