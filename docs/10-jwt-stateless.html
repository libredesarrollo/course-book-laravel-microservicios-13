JWT stateless: la clave pública en vez del salto de red

Capítulo de la serie de microservicios. Tras la resiliencia (docs/09-resiliencia.html), ya supimos caer bien; ahora la pregunta es qué pasaba si ni siquiera hacía falta preguntar: el IdP firma un JWT con RS256, publica su clave pública en un endpoint JWKS, y los relying parties verifican la firma localmente. El salto de red de GET /api/user por cada request desaparece del camino. Todo sigue hablando el mismo contrato del paquete demo/microservices-user-service-client: ni un cambio en los RPs.

El problema que quedó pendiente

Con el diseño de token opaco (b0.6), el flujo regular de un request autenticado en el RP era:

  1. el cliente llega con un token opaco (cadena aleatoria);
  2. el middleware del RP pregunta al IdP GET /api/user — salto de red;
  3. el IdP busca la fila api_tokens por SHA-256 y carga al usuario;
  4. el IdP responde con el dueño del token.

La resiliencia nos protege del paso 2 cuando el IdP está caído. Pero el paso 2 sigue existiendo: con 100 usuarios que abren su listado, y hay N usuarios, son N llamadas de red por nada. El precio es el salto de red por request, y hasta b0.7 quedaba en pie.

¿Qué pasa si, en vez de preguntarle al IdP de quién es el token, el IdP nos entrega un token que ya trae la respuesta y va firmado?

La idea: la identidad viaja en el token

Un JWT es una afirmación firmada: header.payload.signature. El payload dice: "quién es el usuario, quién firma, y hasta cuándo es válido". La firma, con la clave privada del IdP; la verificación, con la clave pública — que puede publicarse sin miedo: lo que protege al sistema es que nadie más tiene la privada, no que nadie vea la pública.

La clave pública va en formato JWKS (JSON Web Key Set), el estándar que usa todo el mundo incluido OIDC: con kty (tipo), n y e (componentes RSA) y un kid (id de la clave) que el RP usa para saber con cuál verificar.

El contrato del paquete se mantiene intacto. Los cambios de b0.7:

CosaAntes (token opaco)Ahora (JWT)
Emitir (login y SSO)Fila aleatoria SHA-256 en api_tokensJWT RS256 firmado por el IdP; no se guarda nada

En el IdP: emitir y publicar

El par de claves

php artisan user-service:jwt-keys genera el par RS2048 en storage/app/jwt/ — privada nunca versionada (el storage/app/.gitignore del Laravel nuevo ya la excluye). El kid se deriva del hash del módulo de la pública: estable mientras dura el par, y distinto para el próximo par. Eso es la rotación: regenerar el par invalida todos los JWT vivos y los RPs refetch al ver un kid desconocido.

La firma

// user-service/app/Services/Jwt/JwtTokenIssuer.php
$payload = [
    'iss' => (string) config('jwt.issuer'),   // user-service: a quién le da validez

    // La foto de identidad: `sub` es el id del usuario; name y email van de
    // conveniencia, para que el RP no pregunte de nuevo.
    'sub' => (string) $user->id,
    'name' => $user->name,
    'email' => $user->email,

    // Momentos: iat = cuándo se emitió, exp = cuándo vence (iat + TTL)
    'iat' => (int) $issuedAt->getTimestamp(),
    'exp' => (int) $expiresAt->getTimestamp(),

    // jti: id único del token; sirve para correlacionar un token en los logs
    // sin exponer su contenido.
    'jti' => bin2hex(random_bytes(16)),
    'device_name' => $deviceName,             // metadata
];

$token = JWT::encode($payload, $this->keys->privateKey(), 'RS256', $this->keys->kid());

La fachada de emisión

El conmutador de modo vive en AccessTokenIssuer.

// user-service/app/Services/Jwt/AccessTokenIssuer.php
public function issue(User $user, string $deviceName): array
{
    if (config('tokens.mode') === 'jwt') {
        $issued = $this->jwtIssuer->issue($user, $deviceName);

        return [
            'token' => $issued['token'],
            'token_type' => 'Bearer',
            'expires_at' => $issued['expires_at']->toIso8601String(),
            'api_token' => null,
        ];
    }

    $opaque = ApiToken::issueFor($user, $deviceName, now()->addMinutes((int) config('tokens.ttl_minutes')));

    return [
        'token' => $opaque['token'],
        'token_type' => 'Bearer',
        'expires_at' => $opaque['model']->expires_at?->toIso8601String(),
        'api_token' => $opaque['model'],
    ];
}

En el paquete: verificar en local

El store de claves pública

JwkKeyStore baja la JWKS una vez, la guarda en la caché del RP durante user-service-client.jwt.jwks_cache_ttl (típico: 1 hora) y, cuando arranca un token con un kid desconocido, fuerza refetch: la rotación no requiere despliegue. Con ttl 0 pregunta por HTTP en cada verificación (el trade-off del cache del middleware ahora para las claves).

El verificador

JwtVerifier usa la misma lib (firebase/php-jwt) que el IdP:

// packages/microservices-user-service-client/src/Jwt/JwtVerifier.php
try {
    JWT::$leeway = max(0, (int) config('user-service-client.jwt.leeway', 10));

    $claims = JWT::decode($token, $this->keys->keySet($this->kidOf($token)));
} catch (\Throwable) {
    return null;   // firma corrupta, expirado, kid desconocido, formato roto
}

if ((string) ($claims->iss ?? '') !== (string) config('user-service-client.jwt.issuer', 'user-service')) {
    return null;
}

return [
    'id' => (int) $claims->sub,
    'name' => (string) $claims->name,
    'email' => (string) $claims->email,
];

La nueva implementación del contrato

// packages/microservices-user-service-client/src/Jwt/JwtIdentityProvider.php
public function authenticate(string $token): ?array
{
    $user = $this->verifier->verify($token);

    if ($user !== null) {
        return $user;
    }

    if (substr_count($token, '.') === 2) {
        // Parecía JWT y no lo es: firmado por otro iss, expirado,
        // corrompido. No hay a quién preguntarle vía HTTP — un JWT no
        return null;
    }

    return $this->clients->authenticate($token);
}

El binding del service provider

// packages/microservices-user-service-client/src/UserServiceClientServiceProvider.php
$this->app->singleton(JwkKeyStore::class);
$this->app->singleton(JwtVerifier::class);

// Desde b0.7 el default verifica JWT localmente (con refetch de JWKS y el
// cliente HTTP de respaldo para los opacos y para emitir).
$this->app->bind(IdentityProvider::class, JwtIdentityProvider::class);

Compatibilidad: los dos modos conviven

No hay interruptor del lado RP, ni memo: el modo lo define el IdP al emitir, y el RP lo elige guiado por la forma del token. Tres segmentos separados por punto → verificación local. Lo demás → flecha del cliente HTTP. Un token opaco emitido con TOKEN_MODE=opaque sigue funcionando como toda la vida; un JWT expirado lo da 401 sin ir a la red (aunque es importante: el middleware cachea los null con el cache_ttl de b0.6 para no repetir verificaciones fallidas).

DELETE /api/tokens sigue siendo el contrato del logout en alguna cases: con un token opaco destruye la fila; con JWT es un no-op que responde 204 igual, para que los consumidores no dependan de lo que te pasa detrás.

El talón de Aquiles: revocar lo que nadie guarda

El precio del stateless es puntual: si no hay filas que borrar, no hay cómo invalidar un token antes de que expire. Mitigamos con el TTL corto (JWT_TTL_MINUTES=15): el máximo daño de un token robado es un cuarto de hora. Y en el flujo web (SSO), el usuario ni lo nota: la sesión del IdP es la del flujo; el JWT viaja con la sesión del navegador, y el logout central del IdP invalida las sesiones de los RPs ya visitados (b0.5).

Verificación real con los tres servicios

Levantados los tres servicios sobre php artisan serve, login real con curl e invocaciones de kill -9 al user-service:

EscenarioModoResultado medido
Login real (POST /api/tokens con credenciales válidas) jwt 201 con JWT en token y cero filas en api_tokens
GET /api/tasks con JWT, request mismo arranque jwt 200 en 180 ms — JWKS fetch + verificación (cache generada)
GET /api/tasks repetida sobre la misma JWKS jwt 200 en 4–6 ms — cero llamadas al IdP
IdP kill -9, JWKS cacheada y verificación local jwt 200 en 4–11 ms — task-service sigue autenticando con el IdP muerto
Lo mismo con token opaco (b0.6) opaque 503 en 5 ms (circuito abierto) o 200 con caché de verificación viva

El quinto renglón es el que se compara contra la historia: el 200 "con el IdP muerto" era un lujo de la caché (60 s); ahora es el camino regular.

Del lado IdP (user-service):

JWT_ISSUER=user-service
JWT_LEEWAY=10
# Si mueves el par de sitio, declara JWT_PRIVATE_KEY / JWT_PUBLIC_KEY. Genera el par con:

Elecciones y precios

  • RS256, no HS256. Con secreto compartido cualquier RP podría fabricar tokens; con par asimétrico solo el IdP firma. El precio: el par vive en disco y hay que generarlo — es exactamente para eso el comando de claves.
  • iss explícito. Un JWT bien firmado de otro emisor se rechaza: redundante con la verificación de firma y por eso defensa en profundidad.
  • Leeway en exp (10 s): los relojes entre máquinas se desvían; el margen e evita rechazar tokens legítimos por segundos. Vale 10 s más de vida para un recién expirado.
  • kid derivado del material: estable mientras dura el par, y independiente del deployment — cada deploy no rota por accidente.
  • Verificar no toca ninguna base de datos. Ni la del RP ni la del IdP: la firma basta. El IdP solo consulta users cuando él mismo recibe su JWT — para que un sub con fila borrada no autentique por un claim viejo.
  • Sin refresh tokens todavía: está el sitio pensado (/api/tokens/refresh) como deja claro config/tokens.php.
