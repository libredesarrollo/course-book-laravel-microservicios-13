Observabilidad entre microservicios: correlation ID, health checks y trazabilidad

Resumen: Al pasar de dos aplicaciones aisladas a dos microservicios que se llaman por HTTP, la pregunta deja de ser "¿ha funcionado?" para pasar a ser "¿qué petición ha provocado este error?". Para responderla hay que poder seguir un único identificador a lo largo de toda la cadena. Este artículo recoge lo que acabamos de implementar: X-Request-Id, health checks, propagación entre servicios y el plan para tener logs correlacionados.

Contexto: proyecto demo-microservicios con user-service y task-service, comunicación HTTP síncrona y autenticación delegada.

1. El problema: peticiones sin rastro

En una app monolítica basta con abrir storage/logs/laravel.log y filtrar por ruta, usuario o excepción. En microservicios la realidad es otra:

  • Una acción en la UI del task-service provoca varias llamadas internas.
  • El task-service delega identidad llamando a GET /api/user del user-service por cada petición autenticada.
  • Si falla la red, el UserServiceUnavailableException aparece solo en los logs del task-service, pero ¿qué cliente lo provocó? no se sabe.
  • Si hay varios usuarios en paralelo, las líneas se entremezclan y resulta imposible reconstruir el camino completo.

Sin un identificador común, depurar entre dos servicios es adivinar.

2. Objetivo del capítulo de observabilidad

El objetivo no es instrumentación completa con OpenTelemetry. Es algo mucho más práctico y necesario:

  1. Poder trazar una petición desde que llega al task-service hasta las llamadas que hace al user-service con el mismo ID.
  2. Saber si los servicios están vivos sin necesidad de autenticar.
  3. Propagar la traza entre ambos servicios por HTTP.
  4. Correlacionar los logs para poder filtrar por request_id y seguir el recorrido completo.

3. Correlation ID: X-Request-Id

La convención es sencilla: usar la cabecera HTTP X-Request-Id.

  • Si llega del cliente (o del servicio que nos llama): se respeta. No se genera uno nuevo.
  • Si no llega: se genera un UUID v4 con Illuminate\Support\Str::uuid().
  • Siempre se devuelve en la respuesta con la misma cabecera X-Request-Id.

Así, cualquier herramienta, proxy o el propio desarrollador puede pasar ese ID y el sistema lo mantendrá durante toda la cadena.

4. Middleware EnsureRequestId

El middleware vive en el paquete de Composer demo/microservices-observability, de modo que los dos servicios comparten exactamente la misma implementación.

<?php

namespace Demo\Microservices\Observability\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Str;
use Symfony\Component\HttpFoundation\Response;

class EnsureRequestId
{
    public function handle(Request $request, Closure $next): Response
    {
        $requestId = $request->header('X-Request-Id');

        if (! is_string($requestId) || $requestId === '') {
            $requestId = (string) Str::uuid();
        }

        $request->attributes->set('request_id', $requestId);

        /** @var Response $response */
        $response = $next($request);

        $response->headers->set('X-Request-Id', $requestId);

        return $response;
    }
}

Se guarda también en los attributes del request para poder accederlo desde servicios como UserServiceClient sin tener que leer la cabecera otra vez.

5. Health checks

Se han añadido endpoints para comprobar la disponibilidad sin pasar por autenticación.

El controller vive en el paquete de observabilidad, así que los dos servicios responden exactamente lo mismo. Lo único que decide cada aplicación es en qué ruta lo monta:

<?php

namespace Demo\Microservices\Observability\Http\Controllers;

use Carbon\Carbon;
use Illuminate\Http\JsonResponse;
use Illuminate\Routing\Controller;

class HealthController extends Controller
{
    public function index(): JsonResponse
    {
        return new JsonResponse([
            'status' => 'ok',
            'service' => config('app.name'),
            'timestamp' => Carbon::now()->toIso8601String(),
        ]);
    }
}

El payload es estático a propósito. Un health check no debe depender de la base de datos, porque el caso interesante es justo el de la base de datos caída: si consultara la base de datos para saber si está bien, no podría distinguir "estoy vivo pero sin base de datos" de "estoy muerto", y el balanceador necesita esa diferencia.

user-service

// routes/api.php
use Demo\Microservices\Observability\Http\Controllers\HealthController;

Route::get('/health', [HealthController::class, 'index']);

// routes/web.php
Route::get('/health', [HealthController::class, 'index']);

task-service

// routes/api.php
Route::get('/health', [HealthController::class, 'index']);

// routes/web.php
Route::get('/health-ui', function () {
    return response('ok', 200)->header('Content-Type', 'text/plain');
});

Como el archivo routes/api.php se monta con el prefijo api, la ruta JSON del task-service queda en /api/health. La de comprobación rápida para el navegador es /health-ui.

El /up que trae Laravel por defecto se mantiene como viene.

6. Propagación al user-service desde task-service

El task-service llama constantemente al user-service: authenticate(), issueToken() y revokeToken() pasan por UserServiceClient (hoy un paquete de Composer, demo/microservices-user-service-client).

Para mantener la traza, se ha añadido un método traceHeaders() que recoge X-Request-Id de la petición entrante al task-service y lo reenvía en todas las peticiones salientes.

private function traceHeaders(): array
{
    $headers = [];

    if (function_exists('request')) {
        $req = request();
        if (! $req) {
            return $headers;
        }

        $requestId = null;

        if ($req->hasHeader('X-Request-Id')) {
            $requestId = $req->header('X-Request-Id');
        } elseif ($req->attributes && $req->attributes->has('request_id')) {
            $requestId = $req->attributes->get('request_id');
        }

        if (is_string($requestId) && $requestId !== '') {
            $headers['X-Request-Id'] = $requestId;
        }
    }

    return $headers;
}

Los tres métodos HTTP (request(), post(), delete()) hacen array_merge($this->traceHeaders(), $headers) para asegurarse de que la cabecera se añade sin romper las ya existentes.

7. Integración en bootstrap/app.php

Los middlewares viven en el paquete de Composer demo/microservices-observability, y el paquete registra los alias request.id y log.context en el Router. Las aplicaciones los referencian por nombre, así que no importan ninguna clase del paquete.

user-service

$middleware->appendToGroup('api', 'request.id');
$middleware->appendToGroup('api', 'log.context');

$middleware->alias([
    'auth.api-token' => AuthenticateApiToken::class,
]);

task-service

$middleware->appendToGroup('web', 'request.id');
$middleware->appendToGroup('web', 'log.context');
$middleware->appendToGroup('api', 'request.id');
$middleware->appendToGroup('api', 'log.context');

$middleware->alias([
    'auth.user-service' => AuthenticateWithUserService::class,
]);

Aplicarlo al grupo api es suficiente porque todas las rutas relevantes pasan por ahí. También se añade al grupo web en el task-service por si se accede directamente desde el navegador y se quiere ver la cabecera en respuestas HTML.

El orden entre los dos importa: request.id va primero porque log.context lee el request_id que el primero deja en los atributos del request. Si se invirtieran, el contexto del log llevaría un request_id nulo.

8. Comprobación en vivo

Con ambos servidores arrancados en local:

$ curl -i http://127.0.0.1:8000/health
HTTP/1.1 200 OK
X-Request-Id: 9b9f3e8e-9b0a-4c56-b7a5-2f9e7b8c9d02
...

Si se pasa un ID explícito, se mantiene:

$ curl -i -H "X-Request-Id: prueba-trazabilidad-123" http://127.0.0.1:8001/api/health
HTTP/1.1 200 OK
X-Request-Id: prueba-trazabilidad-123
...

Al hacer login desde la web del task-service, ese mismo X-Request-Id viaja al user-service en la llamada HTTP que hace UserServiceClient@issueToken. Y con los logs con contexto (sección siguiente), el mismo ID aparece dentro del log de los dos servicios.

9. Logs con contexto

Sin contexto, los logs son así:

Failed login attempt {"email":"ana.torres@example.com","ip":"127.0.0.1","account_exists":true}

El request_id no aparece, así que no se puede cruzar con la respuesta HTTP ni con los logs del otro servicio. La solución es Log::withContext() de Laravel: a partir de ahí, cualquier Log::info/warning/error lleva ese contexto, sin tener que acordarse de pasar el array a mano en cada llamada.

El middleware AttachLogContext

Se ejecuta después de EnsureRequestId. Su trabajo es:

<?php

namespace Demo\Microservices\Observability\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;
use Symfony\Component\HttpFoundation\Response;

class AttachLogContext
{
    public function handle(Request $request, Closure $next): Response
    {
        $requestId = $request->attributes->get('request_id');

        if (! is_string($requestId) || $requestId === '') {
            $requestId = $request->header('X-Request-Id');
        }

        Log::withContext([
            'request_id' => $requestId,
            'service' => config('app.name'),
            'ip' => $request->ip(),
            'method' => $request->getMethod(),
            'path' => $request->path(),
        ]);

        return $next($request);
    }
}

A diferencia de EnsureRequestId, este middleware no modifica la respuesta. Únicamente añade contexto al logger.

El resultado en el log es este:

[2026-10-21 14:31:31] local.WARNING: Failed login attempt {"request_id":"traza-e2e-001","service":"User Service","ip":"127.0.0.1","method":"POST","path":"api/tokens","email":"ana@example.com","account_exists":true}

Con ese request_id se puede filtrar en los logs de los dos servicios y reconstruir la petición completa:

$ grep "traza-e2e-001" task-service/storage/logs/laravel.log user-service/storage/logs/laravel.log

Y como el task-service reenvía la cabecera X-Request-Id al user-service, el mismo ID aparece a los dos lados.

10. Cómo se cierra el capítulo

PasoAcciónRazón
1 AttachLogContext en el paquete de observabilidad Añadir request_id, service, ip, method y path al contexto del log
2 Registrarlo en bootstrap/app.php justo después de request.id Necesita que ya exista el request_id
3 Aplicarlo a los grupos api (y web en task-service) Que se aplique a todas las rutas con lo cual hay trazabilidad
4 Enriquecer algunos logs existentes Probar en vivo que funciona: AuthController (user-service), AuthenticateWithUserService, AuthenticateApiToken
5 Comprobar con curl y ver storage/logs/laravel.log Validar que el mismo request_id aparece desde ambos lados

11. ¿Por qué antes de reintentos?

En UserServiceClient está previsto añadir Http::retry(3, 200) con retryWhen para errores de red. Eso está bien, pero tiene un problema sin trazabilidad:

  • Sin contexto: ConnectionException → ¿es el primer intento o el tercero? Difícil de distinguir.
  • Con request_id + logs con contexto: verás las 3 líneas con el mismo request_id y sabrás que son reintentos de la misma petición.
  • Con propagación cruzada: también podrás buscar ese request_id en los logs del user-service y ver si llegó alguna vez o si nunca salió del task-service.

Por eso se ha optado por logs con contexto antes que reintentos. Es el orden correcto para poder depurar lo que venga después.
