Resiliencia ante la caída del IdP

Capítulo de la serie de microservicios. Tras el SSO (docs/08-que-se-hizo-sso.html), el IdP quedó como la única dependencia capaz de tumbar a toda la aplicación. Este capítulo es lo que hacemos con eso: reintentos, circuit breaker y caché de verificación, todo dentro del paquete demo/microservices-user-service-client, sin que ningún RP cambie su código.

1. El problema que dejó el SSO

Con el login centralizado, cada request web de task-service y billing-service pasa por el middleware, que le pregunta al user-service quién es el dueño del token. Ese diseño evita duplicar el estado de identidad, con una consecuencia directa: si el IdP cae, no se puede autenticar a nadie, ni en la API ni en la web. Y hasta este capítulo, la única protección era un timeout de 3 segundos: cada request esperaba 3 s a un servicio muerto y devolvía un 503 lento. Una caída de un minuto del IdP convertía a toda la demo en un candado con tiempo de espera.

La meta no era evitar la dependencia (es inherente al diseño), sino que la caída sea degradación breve y legible: fallar rápido, reintentar lo seguro y absorber picos con caché. Todo vive en el paquete, así que los servicios RP no cambian ninguna línea de su código de aplicación.

2. Las tres piezas

Toda la política de resiliencia se resuelve en la llamada que el paquete hace al IdP. Las piezas se desactivan de forma independiente poniendo su valor a 0 en el .env.

PiezaQué haceEn qué archivo vive
Reintentos Repite timeouts/5xx en peticiones idempotentes (GET y DELETE). Los POST no se repiten: el código SSO es de un solo uso, y repetirlo da un 400 engañoso. src/UserServiceClient.php → send()
Circuit breaker Con threshold fallos consecutivos de infra queda abierto durante cooldown segundos y rechaza al instante: 503 en milisegundos, no en timeouts. Vencido el cooldown, pasa tráfico de nuevo; un fallo lo reabre. Su estado vive en la caché de la aplicación (file en local), no en memoria del proceso. src/Resiliency/CircuitBreaker.php
Caché de verificación El middleware guarda sha256(token) → usuario durante cache_ttl segundos, y también el resultado negativo (token podrido). Los usuarios visibles dejan de golpear al IdP con el 401 de cada página; el precio declarado es una ventana de hasta cache_ttl segundos para notar una revocación. src/Http/Middleware/AuthenticateWithUserService.php → resolveUser()

3. El código, pieza por pieza

Todo el HTTP del paquete pasa por UserServiceClient::send(), y ahí es donde enganche el breaker y los reintentos. Primero el breaker: consulta antes de ejecutar, y cada intento de conexión fallido y cada 5xx que agota sus reintentos son evidencia. Y toda respuesta recibida, incluso un 4xx, demuestra que el IdP está vivo y lo cierra: el circuito solo se preocupa por la infraestructura.

// packages/microservices-user-service-client/src/UserServiceClient.php
private function send(callable $callback, bool $retryable = false): Response
{
    if ($this->breaker->isBlocked()) {
        throw new UserServiceUnavailableException(
            'El user-service no está disponible (circuito abierto).'
        );
    }

    $attempts = $retryable
        ? 1 + max(0, (int) config('user-service-client.retries', 2))
        : 1;
    $delayMs = max(0, (int) config('user-service-client.retry_delay_ms', 150));

    for ($attempt = 1; ; $attempt++) {
        $last = $attempt === $attempts;

        try {
            $response = $callback();
        } catch (ConnectionException $exception) {
            // Cada intento de conexión fallido es evidencia adicional.
            $this->breaker->recordFailure();

            if ($last) {
                throw new UserServiceUnavailableException(
                    'No se pudo contactar al user-service.',
                    previous: $exception,
                );
            }

            usleep($delayMs * 1000);

            continue;
        }

        // El circuito solo se preocupa por la infraestructura: hasta un
        // 4xx demuestra que el IdP está vivo y responde.
        if ($response->successful() || $response->clientError()) {
            $this->breaker->recordSuccess();

            return $response;
        }

        if ($last || ! $retryable) {
            if ($response->serverError()) {
                $this->breaker->recordFailure();
            }

            return $response;
        }

        usleep($delayMs * 1000);
    }
}

Qué es retryable: request() (GET de /api/user) y delete() (revocación de token) lo son, post() (/api/sso/exchange y /api/tokens) no. Su estado vive en la caché de la aplicación, así que lo comparten todos los requests y workers del proceso:

// packages/microservices-user-service-client/src/Resiliency/CircuitBreaker.php
class CircuitBreaker
{
    private const OPEN_UNTIL = 'user-service-client.circuit.open_until';
    private const FAILURES = 'user-service-client.circuit.failures';

    public function isBlocked(): bool
    {
        return now()->getTimestamp() < (int) Cache::get(self::OPEN_UNTIL, 0);
    }

    public function recordSuccess(): void
    {
        Cache::forget(self::OPEN_UNTIL);
        Cache::forget(self::FAILURES);
    }

    public function recordFailure(): void
    {
        $failures = (int) Cache::get(self::FAILURES, 0) + 1;

        Cache::put(self::FAILURES, $failures, now()->addHours(1));

        if ($failures >= $this->threshold()) {
            Cache::forget(self::FAILURES);

            $cooldown = max(1, (int) config('user-service-client.circuit_cooldown', 30));

            Cache::put(
                self::OPEN_UNTIL,
                now()->getTimestamp() + $cooldown,
                now()->addSeconds($cooldown + 5),
            );
        }
    }
}

Y la pieza del middleware: la caché de la verificación, con su precio declarado en la documentación del método. También se recuerda el resultado negativo, para que un token inútil no repita su 401 contra el IdP.

// packages/microservices-user-service-client/src/Http/Middleware/AuthenticateWithUserService.php
private function resolveUser(string $token): ?array
{
    $ttl = max(0, (int) config('user-service-client.cache_ttl', 60));

    if ($ttl === 0) {
        return $this->users->authenticate($token);
    }

    $key = self::USER_CACHE_PREFIX.hash('sha256', $token);

    $cached = Cache::get($key);

    if ($cached !== null) {
        return $cached['user'] ?? null;
    }

    $user = $this->users->authenticate($token);

    Cache::put($key, ['user' => $user], now()->addSeconds($ttl));

    return $user;
}

4. Comportamiento antes y después

El IdP caído, en los cuatro escenarios posibles:

EstadoAntesAhora
Con la caché de verificación viva (menos de 60 s) 503 lento (timeout de 3 s) 200: el usuario navega sin enterarse de que el IdP ya no está
Sin caché, primer request 503 en 3000 ms 503 en ~340 ms: connection refused es instantáneo y los 2 reintentos (+ backoff de 150 ms) no esperan el timeout
Sin caché, requests siguientes 503 en 3000 ms cada uno 503 en ~5 ms: el circuito ya está abierto y ni se intenta la red
API 503 lento con cuerpo JSON por el handler del RP Lo mismo, solo que rápido: el breaker lanza la misma UserServiceUnavailableException que ya se renderizaba

Nótese la última fila: el circuito no inventa un tipo de error nuevo. Lanza la excepción existente, y cada RP ya sabía renderizarla (503 con una página que explica cómo levantar el IdP). Lo único nuevo es cuándo se lanza.

5. Verificación real con los tres servicios

Ejercicio medido con los tres servidores levantados, login real por el flujo SSO y kill -9 al user-service del IdP:

  1. Fase A (caché viva): matar el IdP y pedir de nuevo la página de tareas con la misma sesión → 200 en 11 ms. El usuario no se entera.
  2. Fase B (sin caché): limpiar la caché de la aplicación y repetir → 503 en 341 ms (3 intentos de conexión, connection refused instantáneo, más backoff). El segundo request → 503 en 5 ms: el circuito ya está abierto.
  3. Fase C (recuperación): levantar de nuevo el IdP → los requests siguen saliendo 503 en 11 ms por circuito abierto; pasados los 30 s del cooldown → 200 en 166 ms, autenticándose en frío contra el IdP.

Todo esto también está respaldado en tests: la suite del paquete (task-service/tests/Feature/UserServiceClientPackageTest.php) cubre el reintento con Http::sequence(), que GET/DELETE reintentan y POST no, el umbral del circuito, la recuperación tras el cooldown, el 503 en frío con el circuito abierto y la caché positiva/negativa del middleware, con un Http::assertSentCount() que prueba que al IdP le llega la cantidad exacta de llamadas.

6. Configuración

En task-service/.env y billing-service/.env (publica la config con php artisan vendor:publish --tag=user-service-client-config si necesitas tocar el archivo):

USER_SERVICE_URL=http://127.0.0.1:8000
USER_SERVICE_TIMEOUT=3
USER_SERVICE_RETRIES=2            # reintentos de peticiones idempotentes
USER_SERVICE_RETRY_DELAY_MS=150   # pausa fija entre reintentos
USER_SERVICE_CACHE_TTL=60         # segundos de caché de verificación (0 = sin caché)
USER_SERVICE_CIRCUIT_THRESHOLD=3  # fallos consecutivos que abren el circuito
USER_SERVICE_CIRCUIT_COOLDOWN=30  # segundos abierto antes de volver a sondear

7. Elecciones y precios

El estado del breaker vive en la caché, no en memoria. Con CACHE_STORE=file, un artisan serve por puerto funciona, y con varios workers de PHP-FPM el breaker queda compartido: todos ven el circuito de la aplicación, no el del proceso.

Fallar en frío es lo correcto para la web: mejor un 503 inmediato con la página de error ya existente que tres segundos colgado por request. Y como el circuito abre al tercer fallo consecutivo, la ventana "lenta" dura un request.

Sin grace period: si el circuito está abierto y la caché también expiró, la respuesta es 503. No se acepta un token sin poder validarlo. La caché de 60 s es el único margen declarado, y es estrictamente a cambio de estar más rápido y no pisar al IdP.

El precio real está documentado donde se decide. La ventana de revocación (ya expuesta en el README) y el coste de la caché están en el PHPDoc de resolveUser() y en la config: que nadie fuerce cache_ttl a 3600 sin leer la advertencia del método.
