El punto de partida

Dos servicios que no se conocen

Sin microservicios

Un solo proyecto, una base de datos, un JOIN y listo.

Funciona. Es rápido de construir. Y cuando un equipo quiere publicar su parte de forma independiente, no hay por dónde empezar.

Con microservicios

Dos procesos, dos bases. Y entonces surge la pregunta que no tiene atajo: ¿cómo sabe el uno que el otro tiene ese dato?

La respuesta obvia —"que lo pregunte"— es exactamente el diseño de este proyecto. Y resulta que no es una solución improvisada: es un patrón real, con un nombre (service client o API Gateway), con sus ventajas y con sus costes.

Lo que sigue es ese patrón, construido entero, midiendo lo que cuesta.

El flujo · fase 1

Inicio de sesión, una vez

  1. 1
    El cliente manda email y contraseña a POST /api/tokens.
  2. 2
    El user-service verifica el hash de la contraseña y emite un token opaco: 64 caracteres hexadecimales aleatorios.
  3. 3
    En la tabla solo se guarda su SHA-256. Si alguien lee la base de datos, no puede suplantar a nadie.
  4. 4
    El token en claro viaja una única vez, en la respuesta 201.
Por qué SHA-256 y no bcrypt: el token no es una contraseña que alguien pueda escoger, son 32 bytes de random_bytes. No hay espacio de búsqueda que recorrer. Con una contraseña elegida por el usuario el ataque de fuerza bruta sí es realista, y ahí sí tocaría Argon2.
El flujo · fase 2

Cada request posterior

  1. 1
    El cliente envía Authorization: Bearer <token>.
  2. 2
    El task-service no puede validarlo: la tabla de tokens no es suya. Así que se lo reenvía al user-service.
  3. 3
    GET /api/user responde 200 {id, name, email} o 401. Es la introspección de tokens de un identity provider.
  4. 4
    El user_id de la tarea sale de la identidad, nunca del cuerpo del request.
  5. 5
    Para una tarea concreta se comprueba la propiedad: si no es tuya, 403.
Y si el user-service está caído, el task-service devuelve 503 en todo. Nadie puede autenticarse. Eso no es un defecto de implementación: es el precio, visible y medible, de no duplicar el estado de identidad.
La pieza clave

Toda la frontera de red vive en un sitio

// app/Services/UserServiceClient.php
class UserServiceClient
{
    /** null si el token no es válido */
    public function authenticate(string $token): ?array;

    public function issueToken(array $credentials): string;
    public function revokeToken(string $token): void;

    private function send(callable $callback): Response;  // ConnectionException -> excepción
}
Los controllers no saben nada del tema. No hay URLs, ni timeouts, ni códigos de error del peer en ningún controller. Es el patrón de un API Gateway: tratar al otro microservicio como si fuera una función local.
La distinción que importa: 401 no es un fallo del servicio, es "este token no vale" y se traduce a null. Cualquier otro status es un problema del peer y lanza excepción. Confundirlos convierte "vuelve a loguearte" en "el sistema está roto".

La lección

Un bug de diseño que la auth silenció

Antes

$validated = $request->validate([
    'user_id' => ['required', 'integer'],
]);

if ($userService->find($validated['user_id']) === null) {
    return response()->json(['error' => ...], 422);
}

$task = Task::create([
    'user_id' => $validated['user_id'],
]);

El cliente decía de quién era la tarea. La validación solo comprobaba que el usuario existiera — no que quien llamara fuera ese usuario.

Ahora

$task = Task::create([
    'title'   => $request->validated()['title'],
    'user_id' => $this->user()->id,
]);

Una validación de existencia no es una autorización. Con autenticación, el user_id dejó de ser un dato que el cliente afirma y pasó a ser una identidad que el sistema resuelve.

Y la llamada explícita a validar user_id desapareció. No es un descuido: el middleware ya preguntó lo mismo por el mismo canal. Preguntarlo otra vez era pagar la latencia otra vez para obtener la misma respuesta. 
$ curl -X POST .../api/tasks -H "Authorization: Bearer $T" \
       -d '{"title":"Secreto de Ana","user_id":999}'
{"title":"Secreto de Ana","user_id":1,...}   # el 999 se descartó
Lo que salió mal

Tres errores que nadie encontró leyendo el código

Fuga de información

Route model binding corre antes del middleware de auth. Un anónimo veía 404 para "no existe" y 403 para "existe pero no es tuya": dos respuestas para un dato que no debía conocer.

→ Resolver el modelo dentro del controller, después de autenticar.

500 en cada request

El grupo api no arranca sesión. Llamar a ->session() ahí lanza excepción. Solo pasaba con token inválido: el camino infeliz, sin cobertura.

→ if ($request->hasSession())

El error que no era error

Un token caducado devolvía 502 "el user-service falló" en lugar de 401. El usuario veía "el sistema está roto" cuando solo tenía que iniciar sesión otra vez.

→ Tratar 401 como identidad inválida, no como caída del servicio.

Los tres los encontraron los tests o un curl, no la lectura. El primero es además un problema de seguridad real que estaba presente en el código.

Hubo un cuarto, más discreto: expires_at sin castear a datetime, que hacía que isExpired() explotara en producción con "Call to a member function isPast() on string".

Mismo cliente, distinto renderizado. Los dos controllers usan el mismo UserServiceClient. Lo único que cambia es cómo se devuelve el resultado: JSON en la API, redirección y error bag en la web.
Degradación explícita. Si el user-service cae, la web muestra una página que dice qué servicio falta y cómo levantarlo, en vez de un error genérico.

Las vistas llevan su CSS inline y no usan @vite: el proyecto no tiene node_modules, así que con el pipeline de Vite las páginas darían "Unable to locate file in Vite manifest". Cero paso de build.

Criterio

Decisiones y el porqué

DecisiónAlternativa descartadaPor qué
Token opaco + SHA-256 JWT Un único dueño del estado de identidad y revocación inmediata. El JWT se justifica cuando hay terceros validando; aquí no los hay.
Validar por HTTP JWT stateless Es el diseño correcto y deja el coste visible en vez de teórico. El salto de red es justo lo que un JWT evita — y ahora se puede medir.
Sin selector de usuario Campo user_id en el formulario Con autenticación la tarea es de quien la crea. Permitir asignarla a otro sería reintroducir el problema que la auth resolvió.
expires_at NOT NULL Columna nullable Un token sin caducidad sirve para siempre. Hacerlo imposible por esquema, no por convención.
SQLite MySQL / PostgreSQL Dos archivos, dos procesos, cero infraestructura. El aislamiento del ejercicio se demuestra igual.
Hacia dónde

El siguiente paso no es RabbitMQ

Primero — barata y evita incidentes

  1. X-Request-Id propagado + métricas
  2. Circuit breaker (de 3 s de espera a 3 ms)
  3. Refresh tokens
  4. API versioning
  5. Contratos de consumidor en CI

Después — solo si el punto 2 duele

  1. RabbitMQ (de síncrono a asíncrono)
  2. Docker + health checks
  3. Octane (por debajo de ~500 req/min no se nota)
  4. Gateway o JWT, si aparece un tercer consumidor
El orden importa: los primeros cinco cuestan horas y evitan incidentes. Octane puede esperar un año sin que nadie lo note. Añadirlo antes es infrastructure por adelantado.
El riesgo estructural que queda: los tests mockean al otro servicio. Si alguien cambia la forma del 401 en el user-service, los tests del task-service seguirán en verde y se rompe en producción. Los contratos de consumidor lo resuelven, y es el paso que más duele no hacer.
