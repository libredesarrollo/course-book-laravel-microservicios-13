Empaquetar módulos con Composer: microservicios Laravel con paquetes locales

Resumen: Cuando dos microservicios comparten código, hay tres caminos: copiar y pegar, un paquete en Packagist, o un paquete local con repositorio path. Este artículo explica el tercero: cómo se extrae el código compartido a packages/, cómo se declara el composer.json de un paquete, cómo lo consumen las aplicaciones, y por qué el resultado es un symlink en lugar de una copia.

Aplicado en el proyecto demo-microservicios, que tiene user-service y task-service con código duplicado de observabilidad.

1. El problema: código duplicado

En el capítulo anterior de observabilidad se añadieron dos middlewares a ambos servicios. El resultado fue esto:

user-service/app/Http/Middleware/EnsureRequestId.php     (18 lineas)
user-service/app/Http/Middleware/AttachLogContext.php    (32 lineas)
task-service/app/Http/Middleware/EnsureRequestId.php     (18 lineas)  <- identico
task-service/app/Http/Middleware/AttachLogContext.php    (32 lineas)  <- identico

Cuatro archivos donde bastaban dos. Y el problema real no es el tamaño:

El problema real es la divergencia. Si mañana hay que cambiar el formato del request_id, hay que recordar cambiarlo en dos sitios. Si se cambia en uno y no en el otro, el task-service genera IDs con un formato y el user-service con otro. Y el síntoma aparece en producción, un martes, sin ningún test que lo detecte.

Ese es el momento en que el código duplicado deja de ser "un poco feo" y pasa a ser un riesgo operativo.

2. Las tres opciones y por qué esta

OpciónVentajasInconvenientes
A. Copiar y pegar Cero infraestructura, funciona siempre Divergencia silenciosa. Es lo que acabamos de tener.
B. Paquete en Packagist Instalable desde cualquier sitio, versionado de verdad Requiere una cuenta, tokens, CI para publicar. Innecesario para un monorepo de 2 servicios.
C. Paquete local con repositorio path Versionable con Git, sin publicar nada, los cambios se ven al instante Hay que declararlo en el composer.json de cada consumidor

Elegimos la C. En un monorepo es la opción estándar: se obtiene el beneficio de la modularidad (una sola copia del código, un solo sitio que cambiar) sin el coste de publicar nada.

El principio de la estructura: en packages/ va lo que es compartido; en app/ va lo que es de cada servicio. Un paquete que solo usa un servicio no es un paquete: es código que se mudó de sitio sin ganancia.

Qué significa cada clave

ClaveValorPor qué
type library Distingue un paquete de código de un proyecto. Composer lo usa para decidir cómo tratarlo.
autoload.psr-4 Demo\\Microservices\\Observability\\ -> src/ El namespace del paquete. Determina dónde busca PHP las clases.
require Solo illuminate/support, illuminate/http e illuminate/routing El paquete usa Str, Log, Request, Response y el Router (para registrar los alias de middleware). No exige laravel/framework en sus dependencias, así que no obliga a instalar el framework completo.
extra.laravel.providers El ServiceProvider Es lo que hace que Laravel descubra el paquete automáticamente. Sin esto, el provider hay que registrarlo a mano en bootstrap/providers.php.
minimum-stability dev Necesario para que Composer acepte la versión @dev del paquete local.
prefer-stable true Prefiere versiones estables de las demás dependencias aunque se permita dev.

Detalle sobre las dependencias: el paquete declara illuminate/support e illuminate/http en lugar de laravel/framework. Es una práctica real: un paquete pequeño que solo necesita el contenedor y las utilidades de HTTP no debería obligar a instalar el framework completo. Aquí la diferencia no se nota porque las aplicaciones ya lo tienen, pero en un paquete publicado la diferencia importa.

Con un matiz, porque la verdad incomoda: que el paquete no declare laravel/framework no significa que no lo use. Los helpers config() y request() no viven en illuminate/support: viven en Illuminate\Foundation. El código nuevo del paquete evita depender de ellos siempre que puede —el controller de health check construye su JsonResponse a mano en vez de usar response(), y el middleware recibe el Redirector y el UrlGenerator inyectados en vez de llamar a redirect()—, pero el UserServiceClient ya usaba request() y config() antes de esta refactorización.

La diferencia práctica: si mañana estos paquetes se quisieran usar en Lumen, o en un proyecto que no tire de Foundation, habría que quitar esos tres o cuatro helpers. Es un trabajo pequeño, pero no es cero, y decir "no depende de Laravel" cuando en realidad depende de Foundation es una forma elegante de mentir.

5. El ServiceProvider

Un ServiceProvider vacío es ruido: existe la convención de que todo paquete Laravel tenga uno, pero un provider que no hace nada no aporta nada. La pregunta correcta no es "¿debe el paquete tener un provider?", sino "¿qué trabajo tiene que hacer el paquete que la aplicación no debería tener que hacer?"

5.1 El provider de observabilidad: registrar la API pública

El trabajo del paquete de observabilidad es publicar sus middlewares bajo un alias concreto. La aplicación lo referencia por nombre y así queda atada al nombre, no a la clase concreta. Si el paquete renombra EnsureRequestId o lo mueve de namespace, las aplicaciones no se tocan.

<?php

namespace Demo\Microservices\Observability;

use Demo\Microservices\Observability\Http\Middleware\AttachLogContext;
use Demo\Microservices\Observability\Http\Middleware\EnsureRequestId;
use Illuminate\Routing\Router;
use Illuminate\Support\ServiceProvider;

class MicroservicesObservabilityServiceProvider extends ServiceProvider
{
    public const ALIAS_REQUEST_ID = 'request.id';

    public const ALIAS_LOG_CONTEXT = 'log.context';

    public function boot(Router $router): void
    {
        $router->aliasMiddleware(self::ALIAS_REQUEST_ID, EnsureRequestId::class);
        $router->aliasMiddleware(self::ALIAS_LOG_CONTEXT, AttachLogContext::class);
    }
}

Y en la aplicación desaparece todo import de clases del paquete:

// bootstrap/app.php
$middleware->appendToGroup('api', 'request.id');
$middleware->appendToGroup('api', 'log.context');

Decisión deliberada: el provider de observabilidad no aplica los middlewares a los grupos api o web automáticamente. Se deja esa decisión en el bootstrap/app.php de cada aplicación.

El motivo: un paquete que decide por ti en qué rutas se aplica es un paquete que impone comportamiento silencioso. Si el día de mañana el user-service quiere el request_id también en las rutas web, se cambia en un sitio visible (bootstrap/app.php) y no dentro de un vendor/ que no controlas.

5.2 El provider del cliente HTTP: enlazar implementaciones y publicar el alias

El del cliente HTTP tiene un trabajo distinto: registrar el cliente como singleton en el contenedor, de forma que se comparta la instancia y su configuración, enlazar la implementación con el contrato que consume la aplicación, y publicar su middleware bajo un alias:

<?php

namespace Demo\Microservices\UserServiceClient;

use Demo\Microservices\UserServiceClient\Contracts\IdentityProvider;
use Demo\Microservices\UserServiceClient\Http\Middleware\AuthenticateWithUserService;
use Illuminate\Routing\Router;
use Illuminate\Support\ServiceProvider;

class UserServiceClientServiceProvider extends ServiceProvider
{
    public const ALIAS_AUTHENTICATE = 'auth.user-service';

    public function register(): void
    {
        $this->mergeConfigFrom(
            __DIR__.'/../config/user-service-client.php',
            'user-service-client'
        );

        $this->app->singleton(UserServiceClient::class);

        // El contrato es lo que consumen la aplicación; la implementación
        // concreta es un detalle que puede cambiar sin tocar a nadie.
        $this->app->bind(IdentityProvider::class, UserServiceClient::class);

        $this->app->singleton(TokenSession::class);
    }

    public function boot(Router $router): void
    {
        // Solo se registra si la aplicación no ha declarado el alias con
        // otro nombre. Así el paquete ofrece un valor por defecto y la
        // aplicación conserva la última palabra.
        if (! array_key_exists(self::ALIAS_AUTHENTICATE, $router->getMiddleware())) {
            $router->aliasMiddleware(self::ALIAS_AUTHENTICATE, AuthenticateWithUserService::class);
        }

        if ($this->app->runningInConsole()) {
            $this->publishes([
                __DIR__.'/../config/user-service-client.php' => config_path('user-service-client.php'),
            ], 'user-service-client-config');
        }
    }
}

Resumen de los dos providers: el de observabilidad publica aliases (la API pública del paquete), el del cliente enlaza implementaciones, publica configuración y además registra su propio alias. Son trabajos distintos y por eso los dos existen. Un provider vacío, en cambio, no hace ninguno de los dos.

5.3 El middleware, también en el paquete

El middleware que autentica preguntando al user-service es la última pieza de la frontera: el cliente HTTP habla con el peer, el contrato abstrae esa frontera y el middleware la engancha al ciclo de vida de una petición de Laravel. Si se quedara en la aplicación, cualquier otro consumidor del paquete tendría que reescribirlo.

Por eso también viaja AuthenticatedUser (la identidad ya tipada) y TokenSession (el ciclo de vida de la sesión web respaldada por un token remoto). La aplicación conserva lo que es suyo: las vistas y las redirecciones.

// task-service/app/Http/Controllers/AuthController.php
public function store(Request $request, TokenSession $session): RedirectResponse
{
    $credentials = $request->validate([
        'email' => ['required', 'email'],
        'password' => ['required', 'string'],
    ]);

    try {
        $session->login($request, $credentials, 'task-service-web');
    } catch (UserServiceErrorException) {
        return back()
            ->withInput($request->only('email'))
            ->withErrors(['email' => 'Credenciales inválidas.']);
    }

    return redirect()->intended(route('tasks.index'));
}

El paquete no renderiza nada: eso sigue siendo de la aplicación.

6. El composer.json de la aplicación

En user-service/composer.json y task-service/composer.json se han añadido dos cosas.

6.1 El bloque repositories

"repositories": [
  {
    "type": "path",
    "url": "../packages/microservices-observability"
  },
  {
    "type": "path",
    "url": "../packages/microservices-user-service-client"
  }
]

La clave "type": "path" le dice a Composer: "este paquete no está en Packagist, está en este directorio de mi disco".

La url es relativa al directorio donde vive el composer.json. Por eso es ../packages/... y no una ruta absoluta: el proyecto se puede clonar en cualquier sitio y sigue funcionando.

6.2 El bloque require

"require": {
  "php": "^8.3",
  "laravel/framework": "^13.17",
  "laravel/tinker": "^3.0",
  "demo/microservices-observability": "@dev",
  "demo/microservices-user-service-client": "@dev"
}

La versión "@dev" es la que le dice a Composer: "de esta dependencia acepto cualquier cosa, incluido un paquete local sin versionar". Es la contrapartida obligatoria de usar un repositorio path con paquetes sin tags.

6.3 Las dos mitades juntas

Una de las dos piezas no basta:

  • El repositories le dice a Composer dónde está el paquete.
  • El require le dice que lo quieres.

Con las dos, Composer puede resolverlo. Con solo una, o no lo encuentra o no lo instala.

7. Por qué un symlink y no una copia

Esta es la parte que conviene entender, porque cambia cómo se trabaja.

Después de composer update, esto es lo que hay en cada servicio:

$ ls -la user-service/vendor/demo/
lrwxr-xr-x  microservices-observability -> ../../../packages/microservices-observability/
lrwxr-xr-x  microservices-user-service-client -> ../../../packages/microservices-user-service-client/

Es un enlace simbólico, no una carpeta. Composer's repositorio path detecta que el destino es un directorio local y crea un symlink en lugar de copiar los archivos.

Lo que eso permite

$ vim packages/microservices-observability/src/Http/Middleware/EnsureRequestId.php
# guardar, y listo: los dos servicios ya usan el cambio

Sin ejecutar composer update. Sin reiniciar nada. Sin riesgo de tener una versión del paquete en vendor/ y otra en packages/.

Lo que hay que vigilar

RiesgoQué pasaCómo se evita
El symlink se pierde al reinstalar Un composer install en limpio lo recrea, pero hay que acordarse de la entrada repositories Está en el composer.json, que sí se versiona
Un composer install sin --no-dev en otro sitio Intenta descargar de Packagist y falla Los paquetes son @dev locales; nunca se descargan, se enlazan
El paquete se "instala" pero el código no cambia Pasa si el composer.json del paquete cambió y no se regenera el autoloader composer dump-autoload
Deployment en producción El symlink no existe en el servidor En el servidor el paquete se instala desde un repositorio real, o se despliega el monorepo completo

8. Migración paso a paso

Los siete pasos que se ejecutaron, por si hay que repetirlo con otro módulo:

  1. Crear el esqueleto del paquete: packages/<nombre>/ con composer.json, README.md y src/.
  2. Copiar el código desde app/ a src/ (copiar, no mover todavía).
  3. Cambiar el namespace de App\Http\Middleware a Demo\Microservices\Observability\Http\Middleware.
  4. Crear el ServiceProvider y declararlo en extra.laravel.providers.
  5. Añadir repositories y require al composer.json de cada aplicación.
  6. Ejecutar composer update demo/microservices-observability en cada servicio.
  7. Actualizar los imports en bootstrap/app.php, borrar los archivos antiguos de app/Http/Middleware/ y verificar con pint y pest.

Copiar antes de borrar. Es un cambio de tres archivos, pero un rm equivocado deja el proyecto sin middlewares y sin error de compilación: el error sale en tiempo de ejecución, en una petición. La verificación final con los tests es lo que convierte esto en un cambio seguro.

9. El cambio de namespace

Antes, en user-service/app/Http/Middleware/EnsureRequestId.php:

<?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Str;
use Symfony\Component\HttpFoundation\Response;

Ahora, en packages/microservices-observability/src/Http/Middleware/EnsureRequestId.php:

<?php

namespace Demo\Microservices\Observability\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Str;
use Symfony\Component\HttpFoundation\Response;

Y en user-service/bootstrap/app.php:

use App\Http\Middleware\AuthenticateApiToken;
use Demo\Microservices\Observability\Http\Middleware\AttachLogContext;
use Demo\Microservices\Observability\Http\Middleware\EnsureRequestId;

El namespace del paquete tiene que incluir el del consumidor, porque Composer solo puede mapear un prefijo de namespace a un directorio. Por eso el paquete se llama Demo\Microservices\Observability\ y no simplemente Observability\: deja claro de quién es el código.

10. Lo que NO se empaquetó (y por qué)

Esta es la parte del trabajo que más conviene revisar, porque lo natural es empaquetar de más.

Código¿Paquete?Razón
EnsureRequestId Sí Idéntico en ambos servicios, sin dependencias del servicio
AttachLogContext Sí Idéntico en ambos servicios
UserServiceClient + excepciones Sí Un tercer microservicio necesitará el mismo cliente. Hoy solo lo usa uno, pero la lógica ya está probada.
AuthenticateApiToken No Solo tiene sentido en el user-service: valida tokens contra su propia base de datos.
AuthenticateWithUserService Sí Es la última pieza de la frontera con el user-service: sin ella, cada consumidor del paquete tendría que reescribir el middleware.
HealthController Sí Idéntico en ambos servicios (94% de líneas en común). Si cada uno escribiera el suyo, acabarían respondiendo de forma distinta.
Rate limiting y config/tokens.php No Específico del servicio de identidad.
DTO AuthenticatedUser Sí Va de la mano del middleware que lo produce: es la identidad que el user-service confirmó por HTTP.

La trampa: AuthenticateApiToken y AuthenticateWithUserService se parecen mucho. Los dos autentican una petición, los dos devuelven 401, los dos usan un token Bearer. La tentación es unificarlos en un middleware con un if dentro:

// NO: el día que este middleware crezca, será ilegible
if ($service === 'user-service') { ... } else { ... }

Son responsabilidades distintas que happen en direcciones distintas: uno consulta su propia base de datos, el otro llama por HTTP a otro servicio. Unificarlos introduciría una dependencia entre ambos servicios en el mismo archivo, que es exactamente la acoplamiento que los microservicios intentan evitar.

11. Verificación

Tras la migración, en ambos servicios:

$ vendor/bin/pint
{"tool":"pint","result":"passed"}

$ vendor/bin/pest --compact
{"tool":"pest","result":"passed","tests":28,"passed":28,"assertions":102}
{"tool":"pest","result":"passed","tests":34,"passed":34,"assertions":88}

Los tests no se tocaron. Ni se cambiaron las aserciones, ni los nombres, ni los helpers de tests/Pest.php. Esa es la comprobación que importa: si la extracción del paquete hubiera cambiado un comportamiento, algún test habría caído.

Y la cadena de observabilidad sigue intacta: el request_id se sigue generando, se sigue propagando al user-service y los logs siguen llevan el contexto.

12. El segundo paquete: el cliente del user-service

El primer paquete era el caso fácil: dos middlewares idénticos. El segundo es distinto, porque el código no estaba duplicado: el UserServiceClient solo vivía en el task-service.

La pregunta era: ¿aporta algo moverlo a un paquete?

Sí, por una razón concreta: en cuanto exista un tercer microservicio que también necesite validar tokens, tendrá que escribir el mismo cliente, o copiarlo. Un paquete con contrato resuelve las dos cosas de golpe: el tercer servicio lo instala y ya.

12.1 El contrato: IdentityProvider

La parte interesante no es mover la clase, sino qué consume la aplicación. Antes, el middleware y el controller dependían de la clase concreta:

use App\Services\UserServiceClient;

public function __construct(private readonly UserServiceClient $users) {}

Ahora dependen del contrato:

use Demo\Microservices\UserServiceClient\Contracts\IdentityProvider;

public function __construct(private readonly IdentityProvider $users) {}

El ServiceProvider del paquete hace el enlace:

$this->app->singleton(UserServiceClient::class);

// El contrato es lo que consumen la aplicación; la implementación
// concreta es un detalle que puede cambiar sin tocar a nadie.
$this->app->bind(IdentityProvider::class, UserServiceClient::class);

Por qué importa. Con la clase concreta, cambiar el transporte —de HTTP a AMQP, o a un gateway— obligaba a tocar los controllers. Con el contrato, se cambia el binding y nadie más se entera. Es la diferencia entre depender de una implementación y depender de una abstracción.

12.2 La configuración: el paquete trae la suya

El cliente leía config('services.user_service'), una clave de la aplicación que el paquete no controla. Al moverlo, el paquete trae su propio archivo:

// packages/microservices-user-service-client/config/user-service-client.php
return [
    'url' => env('USER_SERVICE_URL', 'http://127.0.0.1:8000'),
    'timeout' => (int) env('USER_SERVICE_TIMEOUT', 3),
    'client' => env('USER_SERVICE_CLIENT', 'app'),
    'callback_url' => env('USER_SERVICE_CALLBACK_URL'),
    'sso_start_route' => env('USER_SERVICE_SSO_START_ROUTE', 'sso.start'),
];

Y el ServiceProvider lo fusiona y lo hace publicable:

$this->mergeConfigFrom(
    __DIR__.'/../config/user-service-client.php',
    'user-service-client'
);

$this->publishes([
    __DIR__.'/../config/user-service-client.php' => config_path('user-service-client.php'),
], 'user-service-client-config');

Las variables de entorno no cambian: sigue siendo USER_SERVICE_URL y USER_SERVICE_TIMEOUT. Los ficheros .env de los servicios siguen siendo válidos sin tocar nada.

Las claves client, callback_url y sso_start_route son las que necesita el flujo SSO: con qué nombre se presenta el RP ante el IdP, a qué URL vuelve el código y qué ruta local arranca el flujo. Si sso_start_route se deja vacía, el middleware responde siempre 401 en JSON, sin redirigir: es lo que necesita una aplicación que solo expone API.

12.4 El user-service no necesita el cliente

Detalle que conviene señalar: el user-service es el proveedor de identidad. No tiene a nadie a quien preguntar. Así que de su composer.json se quitó el paquete del cliente, y del repositories también:

// user-service/composer.json
"require": {
  "php": "^8.3",
  "laravel/framework": "^13.17",
  "demo/microservices-observability": "@dev"
},

  {
    "type": "path",
    "url": "../packages/microservices-observability"

Instalar una dependencia que no se usa es ruido: obliga a composer install a resolver algo que no aporta nada.

Tras las dos extracciones:

14. Siguiente paso

Con el código compartido empaquetado, el orden natural es:

  1. Un tercer microservicio que consuma el paquete IdentityProvider sin escribir ni una línea de cliente HTTP. Es la prueba de que el empaquetado sirve para algo.
  2. Extraer más módulos si aparece duplicación real: el DTO AuthenticatedUser es el siguiente candidato, cuando lo use un segundo servicio.
  3. Circuit breaker y reintentos en el cliente, ahora que ya es un punto único y fácil de modificar.

Nota: el orden importa. EnsureRequestId debe ejecutarse antes que AttachLogContext, porque el segundo lee el request_id que el primero deja en los atributos del request. Si se invirtiera, el contexto del log llevaría un request_id nulo y la trazabilidad se perdería en silencio.
