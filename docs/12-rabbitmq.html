RabbitMQ: el mismo contrato, broker de verdad

Capítulo de la serie de microservicios. En b0.9 el outbox y la idempotencia quedaron amarrados con colas de database: cada servicio drenaba su propia tabla jobs. Este capítulo compra la promesa de entonces — "migrar a RabbitMQ es cambiar el config('queue'), la aplicación no se entera" — y la cumple: los jobs viajan por un broker real, sin tocar una línea de dominio.

Lo que cambia y lo que no

Queda igualCambia
El outbox: el evento task.completed sigue naciendo en la transacción de la tareaEl transporte de jobs: la tabla jobs de cada servicio deja de guardar mensajes
El webhook firmado con HMAC y su middleware events.verifyEl QUEUE_CONNECTION: de database a rabbitmq
CreateInvoiceFromEvent, SendTaskCompletedEmail y sus reintentosEl demonio local: RabbitMQ corre en Docker, no en el sqlite del servicio
La idempotencia: cache anti-replay + UNIQUE en invoices.event_idNada más. Ni exporters, ni interfaces, ni un solo método de dominio

Esta es la tesis del capítulo: al comprar colas en b0.9, el sistema ya hablaba un contrato (at-least-once + reintentos + idempotencia en el receptor). El broker cumple ese mismo contrato por hardware; las aplicaciones no se enteran.

El broker: docker compose con management UI

RabbitMQ puesto en pie en la raíz del proyecto:

# docker-compose.yml (raíz del repo)
services:
  rabbitmq:
    image: rabbitmq:4-management
    container_name: demo-rabbitmq
    ports:
      - "5672:5672"      # AMQP
      - "15672:15672"    # management UI (guest/guest)
    volumes:
      - rabbitmq-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 10s
      timeout: 10s
      retries: 5

volumes:
  rabbitmq-data:

El arranque requiere Docker Desktop encendido. Con el daemon vivo:

docker compose up -d
# La UI queda en http://127.0.0.1:15672 (guest/guest)
# Y el chequeo de vida:
docker exec demo-rabbitmq rabbitmqctl list_queues --quiet name messages_ready messages_unacknowledged

El paquete del driver y su instalación

El driver oficial para Laravel es vladimir-yuldashev/laravel-queue-rabbitmq — su v15.0.2 exige illuminate/queue ^13 y php-amqplib 3.6. En los dos servicios que hablan en colas (task y billing; el IdP no tiene):

# task-service/ y billing-service/, por separado
composer require vladimir-yuldashev/laravel-queue-rabbitmq:^15.0.2

El paquete registra su conector y hace mergeConfigFrom sobre queue.connections.rabbitmq, así que declarar la conexión en el propio config/queue.php del servicio es la forma cache-safe de explicitarla — y la forma que el curso usa.

La conexión rabbitmq en config/queue.php

Igual en task-service y billing-service:

// config/queue.php (ambos servicios)
'rabbitmq' => [
    'driver' => 'rabbitmq',
    'queue' => env('RABBITMQ_QUEUE', 'default'),
    'hosts' => [
        [
            'host' => env('RABBITMQ_HOST', '127.0.0.1'),
            'port' => env('RABBITMQ_PORT', 5672),
            'user' => env('RABBITMQ_USER', 'guest'),
            'password' => env('RABBITMQ_PASSWORD', 'guest'),
            'vhost' => env('RABBITMQ_VHOST', '/'),
        ],
    ],
    'options' => [],
    'worker' => env('RABBITMQ_WORKER', 'default'),
],

La llave .env que lo decide todo

# .env de task-service y billing-service
QUEUE_CONNECTION=rabbitmq

Con eso, los comandos de siempre no cambian ni un carácter: el worker sigue siendo php artisan queue:work — ahora lee la conexión del env. Timeout de puerto 5672 y UI de management quedan fuera del código. Para volver al mundo de b0.9 solo cambia la llave de vuelta (QUEUE_CONNECTION=database), porque la tabla jobs y el driver database siguen respaldados en la config.

Cómo declaran las colas a sí mismas

El driver no necesita pre-crear colas a mano: el pushRaw de RabbitMQQueue llama declareDestination, y si la cola no existe la declara durable antes de publicar. Por eso, despachar SendTaskCompletedEmail a la cola mails sin worker en pie crea la cola en el broker y el mensaje sobrevive allí. La management UI lo muestra: colas default, mails, invoices y sus lateralidades mails.delay.5000, mails.delay.15000 para reintentos con backoff — el driver implementa el delay de Laravel con colas de TTL y deadletter.

Verificación real: tres saltos y facturas

  1. Tarea 11 completada vía API con el JWT (PUT /api/tasks/11): 52.2 ms, la respuesta no espera al email ni a billing.
  2. php artisan outbox:dispatch en task-service: Entregas nuevas: 1 (128 ms) — webhook firmado de por medio; el flujo de b0.9 intacto.
  3. El broker recibe: mails 1 y invoices 1 listas, las colas se declararon solas.
  4. Workers con el comando nuevo: php artisan queue:work rabbitmq --queue=mails,default --stop-when-empty en task-service → SendTaskCompletedEmail DONE 44ms; y php artisan queue:work rabbitmq --queue=invoices --stop-when-empty en billing-service → CreateInvoiceFromEvent DONE 19ms → factura 6 con amount 10.

Y una trampa real del capítulo: el worker arrancado fuera del directorio del servicio no encuentra ni BD ni env — php artisan queue:work drena el sqlite del directorio donde esté parado. Los comandos corren dentro de cada servicio.

La prueba de honor: el worker muere, el mensaje vuelve

El contrato del broker es at-least-once y aquí está la evidencia de laboratorio:

  1. Un mail real en la cola: mails 1 ready.
  2. Un consumidor que toma el mensaje y no lo reconoce: RabbitMQ lo marca unacked y no lo deja listo de nuevo mientras el consumidor viva.
  3. kill -9 al consumidor: al caer la conexión, RabbitMQ libera el mensaje → mails: 0 unacked → 1 ready. El mensaje no se perdió; el broker lo devolvió.
  4. El worker normal de Laravel lo procesa: SendTaskCompletedEmail DONE 47.57ms — el mail llega una vez.

Un detalle que vale la nota al pie: esa redelivery no le incrementa los attempts del payload de Laravel — el contador de reintentos del job no se entera; es del broker. Los dos niveles (reintentos de job y redelivery de broker) viven por separado.

La idempotencia no se compra; se mantiene

Se re-despachó CreateInvoiceFromEvent con el mismo event_id ya facturado. El job corrió, respondió DONE en 14 ms y no creó factura doble: la UNIQUE en invoices.event_id más el catch de UniqueConstraintViolationException hicieron su trabajo bajo el broker, igual que con colas de database. La responsabilidad de "una sola vez" no migró al broker: sigue cargada en el receptor.

Elecciones y precios

  • Driver swap, motivo de este capítulo. Webhooks del paquete intactos; nadie del dominio lee RabbitMQ. El precio: para que valga aquí, RabbitMQ tiene que estar en pie — sin Docker el broker no existe y toca revolver de vuelta a QUEUE_CONNECTION=database.
  • Reintentos de job en el driver delay-queues. El backoff [5, 15] del mail se refleja como mails.delay.5000 — no es una tabla delayed como en database; la cola lateral retiene el mensaje con TTL, y al expirar lo reenvía por su dead-letter a la cola de destino.
  • El outbox:dispatch no cambió. El webhook es HTTP, así que sus reintentos siguen siendo del despachador (config events). Publicar los eventos por un exchange AMQP — el broker gestionando la entrega del webhook — es un capítulo aparte: ahí sí el paquete de eventos cambia de forma.
  • Seguridad del broker queda para producción. guest en vhost / sirve para el demo: el cambio de usuario, TLS y virtual hosts por servicio no afecta el código de los jobs.
  • Los tests no necesitan broker. El phpunit.xml fija QUEUE_CONNECTION=sync; las suites de los tres servicios (91/215, 65/220, 17/53) quedaron verdes sin tocar Docker — las pruebas ni se enteran de que el broker existe.
