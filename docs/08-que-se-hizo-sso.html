SSO con un IdP central: qué se hizo y por qué (Single Sign-On (en español, Inicio de Sesión Único).)

RP significa Relying Party (Parte Confiante) e IdP significa Identity Provider (Proveedor de Identidad).

Resumen: el proyecto tenía tres microservicios, pero también tres formularios de login. Cada servicio validaba el mismo token contra el mismo user-service y, aun así, al pasar de uno a otro había que volver a escribir la contraseña. Este capítulo cuenta cómo se resolvió: el user-service pasó a ser un Identity Provider con login único, y los demás servicios quedaron como relying parties que no conocen usuarios, no guardan contraseñas y no tienen pantalla de login.

El resultado es un SSO en miniatura: un código de un solo uso viaja por la URL, se canjea por un token propio de cada servicio, y cerrar sesión en cualquiera de ellos cierra la sesión central. No hay JWT, no hay OAuth completo, y esa es parte de la gracia: entender el mecanismo antes de delegarlo en un proveedor.

1. El problema: tres servicios, tres logins

La arquitectura anterior tenía una virtud y un defecto. La virtud: la identidad era propiedad de un solo servicio, el user-service, y los demás validaban el token preguntándoselo por HTTP. El defecto: el acto de iniciar sesión estaba duplicado en cada consumidor.

task-service tenía su AuthController, su vista auth/login, su ruta /login y su modelo User. billing-service tenía exactamente lo mismo, copiado. Ambos pedían credenciales y las reenviaban a user-service. El servicio dueño de la identidad, en cambio, no tenía formulario de login.

Eso producía tres efectos que se notaban en el uso normal de la aplicación:

  1. Re-login constante. Entrar a facturas desde tareas obligaba a teclear la contraseña otra vez, aunque las credenciales fueran las mismas y el validador fuera el mismo.
  2. Sesiones que no se hablaban. Cerrar sesión en un servicio no cerraba nada en el otro. Cada uno tenía su cookie y su almacén, y nadie coordinaba el cierre.
  3. Credenciales en tres sitios. Aunque solo el IdP las verificara, cada relying party seguía teniendo un formulario donde se escribían, una ruta que las recibía y un controller que las manejaba.

El diagnóstico es incómodo: no era un problema de protocolo, era un problema de dónde vive la responsabilidad. Mientras el login viva en cada servicio, el SSO no puede existir, porque no hay una sesión central a la que apelar.

2. La regla que ordena todo

Antes de tocar código se fijó una regla, y todo lo demás salió de ella:

El login y los datos de usuario viven solo en user-service. Ningún otro servicio tiene formulario de login, rutas /login, modelo User, tabla users ni acceso directo a la base de datos de identidad.

Un relying party puede hacer exactamente cuatro cosas: redirigir al IdP, recibir un código, canjearlo por un token propio y guardar ese token en su sesión local. Nada más. Todo lo que necesita saber de una persona se lo pregunta al IdP por HTTP.

Esta restricción tiene una consecuencia práctica valiosa: si mañana se añade un cuarto servicio, no hay que copiar un formulario ni una tabla. Se declaran tres rutas y el paquete hace el resto. El coste de la identidad deja de multiplicarse por el número de servicios.

3. El flujo completo, paso a paso

El mecanismo es una versión simplificada del flujo Authorization Code de OAuth 2.0. La diferencia principal es que aquí el cliente es interno y el IdP está hecho a medida, así que se omiten state, nonce y PKCE.

Navegador                task-service (RP)              user-service (IdP)
    |                          |                                |
    | GET /tasks (sin sesión)  |                                |
    |------------------------->| middleware auth.user-service   |
    | 302 /sso/start           |                                |
    |<-------------------------|                                |
    | GET /sso/start           |                                |
    |------------------------->| SsoStartController             |
    | 302 /authorize?client=task&redirect_uri=...                |
    |<-------------------------|                                |
    | GET /authorize...        |                                |
    |---------------------------------------------------------->|
    |                          |            ¿sesión SSO?        |
    |                          |            NO -> 302 /login     |
    | 302 /login?client=task&redirect_uri=...                    |
    |<----------------------------------------------------------|
    | GET /login (formulario)  |                                |
    |---------------------------------------------------------->|
    | POST /login (email+pass) |                                |
    |---------------------------------------------------------->| Auth::attempt
    |                          |                                | emite code (60 s)
    | 302 redirect_uri?code=XYZ|                                |
    |<----------------------------------------------------------|
    | GET /sso/callback?code=XYZ                                |
    |------------------------->| SsoCallbackController          |
    |                          | POST /api/sso/exchange         |
    |                          |------------------------------->| valida code + client
    |                          |                                | crea token del RP
    |                          |<-------------------------------| 201 {token, user}
    |                          | loginWithToken() -> sesión     |
    | 302 /tasks               |                                |
    |<-------------------------|                                |

Leído en orden, el flujo dice esto:

  1. El middleware del RP no encuentra token en la sesión. En vez de mostrar un formulario, manda al navegador a /sso/start.
  2. SsoStartController construye la URL del IdP con dos datos: el nombre del cliente (task) y la URL exacta a la que debe volver.
  3. El IdP mira su propia sesión. Si no existe, manda al login. Si existe, salta el formulario y emite el código ahí mismo.
  4. El login valida las credenciales con Auth::attempt(), regenera la sesión y, si venía un cliente, emite un código y redirige al RP.
  5. El RP recibe ?code=... y lo canjea en POST /api/sso/exchange. Ese canje es backchannel: servidor a servidor, sin navegador de por medio.
  6. El IdP valida el código, comprueba que pertenece a ese cliente y emite un token nuevo, exclusivo de ese RP.
  7. El RP guarda el token en su sesión con loginWithToken(), que regenera el identificador de sesión, y redirige a donde el usuario quería ir.

El detalle que elimina el re-login es el paso 3. La segunda vez que el navegador visita el IdP, ya hay sesión SSO, así que el formulario no aparece. El usuario ve una redirección y aterriza autenticado en el otro servicio. No hay contraseña, no hay token compartido: solo un código de un solo uso que se consume en el canje.

4. El IdP: piezas y endpoints

El user-service dejó de ser un servicio sin interfaz. Ahora tiene la única pantalla de login del sistema y tres responsabilidades nuevas: validar a quién redirige, emitir códigos y canjearlos.

4.1 La whitelist de clientes

La primera pieza es una configuración explícita. Sin ella, /authorize sería un open redirect: cualquiera podría enviar a un usuario autenticado a un dominio arbitrario con un código válido en la URL.

// user-service/config/sso.php
return [
    'clients' => [
        'task' => [
            'http://127.0.0.1:8001/sso/callback',
            'http://localhost:8001/sso/callback',
        ],
        'billing' => [
            'http://127.0.0.1:8002/sso/callback',
            'http://localhost:8002/sso/callback',
        ],
    ],
    'ticket_ttl' => (int) env('SSO_TICKET_TTL', 60),
];

La comparación es exacta, no por prefijo ni por dominio. Se aceptan las variantes 127.0.0.1 y localhost porque en desarrollo conviven las dos, pero no hay comodines. Añadir un relying party es añadir una entrada aquí, y esa fricción es deliberada: el registro de clientes es una decisión de seguridad, no un detalle de configuración.

4.2 El emisor de códigos

SsoTicketIssuer concentra la parte delicada: validar, rotar y hashear. No devuelve un modelo, devuelve el código en claro una sola vez, porque después solo existirá su hash.

public function issue(User $user, string $client, string $redirectUri): string
{
    // 1. El cliente debe existir y el destino debe estar en su whitelist.
    // 2. Un código nuevo invalida los pendientes del mismo usuario y cliente.
    // 3. Se genera el código y se guarda solo su SHA-256.

    $code = Str::random(64);

    SsoTicket::query()->create([
        'code_hash' => hash('sha256', $code),
        'user_id'   => $user->id,
        'client'    => $client,
        'expires_at' => now()->addSeconds((int) config('sso.ticket_ttl', 60)),
        'used_at'   => null,
    ]);

    return $code;
}

La rotación merece una frase: si el usuario pulsa dos veces o recarga el authorize, no se acumulan códigos vivos. El anterior se borra. Un código pendiente por usuario y cliente es suficiente y reduce la superficie de ataque.

4.3 El ticket

La tabla sso_tickets guarda code_hash (único), user_id, client, expires_at y used_at. En una iteración anterior tenía además token_id, el token que había usado el primer servicio para pedir el ticket. Se eliminó: el flujo actual no depende de que el usuario llegue con un token previo, porque el navegador va directo al IdP y allí ya hay una sesión. Atar el ticket a un token de origen rompía justamente el caso de "entrar primero por billing".

4.4 Los endpoints

MétodoRutaAuthQué hace
GET /login guest El único formulario de login del sistema.
POST /login throttle:6,1 Autentica y, si trae client y redirect_uri, redirige con código.
GET /authorize sesión web Sin sesión redirige al login; con sesión emite el código.
GET/POST /logout — Cierra la sesión central y vuelve al redirect_uri.
POST /api/sso/exchange pública Canjea {code, client} por un token del relying party.
POST /api/tokens pública Login para clientes que no son navegador (CLI, Postman, apps).

Se conservó POST /api/tokens a propósito. El flujo SSO resuelve el navegador, pero una herramienta de línea de comandos no puede seguir redirecciones ni mantener una cookie de sesión del IdP. Ese endpoint ya tenía rate limit por cuenta y por IP, TTL de token y tests; eliminarlo habría roto un caso de uso legítimo para ganar nada.

5. El paquete: la frontera compartida

Los relying parties no implementan el flujo. Lo consume del paquete demo/microservices-user-service-client, que ya encapsulaba el cliente HTTP, el middleware y la sesión con token remoto. Se le añadieron tres controllers y se ajustó el contrato.

// El contrato: el RP no conoce la implementación HTTP.
public function exchangeCode(string $code, string $client): ?array;

// La sesión: el token ya viene emitido, no se piden credenciales.
public function loginWithToken(Request $request, string $token): void;

// El cierre: revoca el token del RP y destruye su sesión local.
public function logout(Request $request): void;

La decisión de devolver null en los estados 400, 401, 404 y 422 es la misma que ya se usaba en authenticate(): un código inválido no es una caída de infraestructura, es una respuesta de negocio. El controller lo traduce a un 401 y sigue. Los errores 5xx, en cambio, lanzan excepción y terminan en un 503, porque ahí sí hay un problema del sistema.

El paquete también trae los tres controllers del flujo. La aplicación solo declara las rutas y elige el nombre del cliente:

Route::get('/sso/start', SsoStartController::class)->name('sso.start');
Route::get('/sso/callback', SsoCallbackController::class)->name('sso.callback');
Route::post('/logout', SsoLogoutController::class)->name('logout');

Se eliminó login_route de la configuración. Ya no existe una pantalla de login local a la que redirigir; en su lugar hay sso_start_route, que apunta al inicio del flujo. Es un cambio pequeño en el archivo, pero grande en el significado: el paquete dejó de asumir que cada aplicación tenía su propio login.

6. Los relying parties: lo que se borró

La parte más elocuente del cambio no es lo que se añadió, sino lo que se pudo borrar. En task-service y billing-service desaparecieron:

Archivo eliminadoPor qué
app/Http/Controllers/AuthController.php El login lo hace el IdP; el RP no recibe contraseñas.
app/Models/User.php y UserFactory.php El RP no es dueño de usuarios, solo recibe una identidad ya validada.
database/migrations/*_create_users_table.php No debe existir una segunda tabla de identidad.
config/auth.php Sin guard local de usuarios no hay nada que configurar.
resources/views/auth/ La única vista de autenticación vive en el IdP.
SsoBridgeController.php (task) y SsoCallbackController.php (billing) El flujo ya es genérico y vive en el paquete.

En su lugar quedan tres rutas finas y una navegación que cruza de servicio con config('services.billing.url') y config('services.task.url'). El botón "Facturas" del task-service ya no pide un ticket por detrás: es un enlace normal al otro servicio, y el SSO hace el resto.

Hay una consecuencia de modelo de datos que conviene decir en voz alta: los relying parties siguen guardando user_id en sus tablas, pero ya no tienen una tabla de usuarios donde buscarlo. Ese número es una referencia opaca que solo el IdP puede resolver. La verificación de que existe ocurre en el middleware, en el mismo request, no en el formulario de creación.

7. Seguridad del código

El código SSO es una credencial temporal. Se trató como tal, con las mismas reglas que los tokens opacos del proyecto.

RiesgoMedida
Reutilización used_at se marca en el canje; el segundo intento responde 400.
Ventana de ataque TTL de 60 segundos. Suficiente para el redirect y el canje, corto para todo lo demás.
Fuga desde la base de datos Solo se guarda sha256(code). En claro existe únicamente en la respuesta.
Open redirect Cada cliente tiene su redirect_uri exacta en la whitelist.
Código cruzado entre clientes El canje exige que client coincida con el del ticket.
Acumulación de códigos Emitir uno nuevo borra los pendientes del mismo usuario y cliente.
Session fixation loginWithToken() regenera el id de sesión antes de guardar el token.
Credenciales en tránsito El token nunca viaja por la URL; solo el código.

Hay una limitación que no se esconde: el código viaja en la query string y, por tanto, puede quedar en el historial del navegador o en un log de acceso. Es exactamente lo que OAuth mitiga con un TTL muy corto y un solo uso. Aquí se aplican las dos cosas, pero un despliegue real añadiría HTTPS obligatorio y quizá state para proteger el callback.

8. Single logout

Cerrar sesión dejó de ser un acto local. El relying party no intenta cerrar sesiones ajenas; delega en el dueño de la sesión central:

POST rp/logout
  -> TokenSession::logout() revoca el token del RP y destruye su sesión local
  -> 302 al /logout del IdP con redirect_uri
  -> el IdP destruye la sesión SSO
  -> vuelve al RP, que ya no tiene sesión

La clave es el orden. Primero se limpia lo local y se revoca el token propio; después se pide al IdP que cierre la sesión compartida. Si el IdP estuviera caído, el usuario quedaría fuera del servicio que pulsó el botón, y el token huérfano caducaría por su cuenta. Es una degradación aceptable: cerrar sesión nunca debe fallar por una dependencia externa.

Lo que este diseño no hace es avisar a los demás servicios. No hay back-channel: si el usuario tenía sesión en tres relying parties, los otros dos conservan su token local hasta que el IdP lo rechace en su siguiente request. Un OIDC completo usaría front-channel o back-channel logout para propagar el cierre. Aquí se eligió la versión honesta y simple, y se documenta la diferencia en vez de fingir que no existe.

9. Decisiones de diseño

El navegador va al IdP, no el servidor. La iteración anterior hacía que task-service pidiera el ticket server-to-server con su token. Funcionaba, pero solo si el usuario ya estaba dentro de task. El flujo actual permite entrar primero por cualquier servicio, porque el IdP es el punto de entrada y el dueño de la sesión.

Un token por relying party. Billing recibe su propio token (device_name = billing-sso), no el de task. Revocar uno no afecta al otro. Es el mismo principio que OAuth: access tokens por cliente, no una credencial compartida.

El ticket no está atado al token de origen. Atarlo parecía más seguro, pero impedía el caso normal: el usuario llega al IdP sin token previo de ningún RP. La seguridad real está en la sesión del IdP, en la whitelist y en el TTL, no en el token que originó el viaje.

La whitelist vive en configuración. Para una demo es explícita y fácil de leer. En producción sería un registro de clientes en base de datos, con scopes y secretos. El código ya está separado para que ese cambio no toque los controllers.

Se conserva el login por API. El SSO es para navegadores. Un cliente programático no puede seguir redirecciones ni mantener cookies del IdP, así que POST /api/tokens sigue siendo la puerta para ese caso.

10. Verificación

La suite se amplió en los tres servicios. El IdP ganó un archivo dedicado al flujo, y los relying parties reemplazaron los tests de formulario por tests de SSO y canje.

cd user-service    && php artisan test --compact   # 53 tests
cd task-service    && php artisan test --compact   # 67 tests
cd billing-service && php artisan test --compact   # 9 tests

En el IdP, tests/Feature/SsoFlowTest.php cubre el login, el formulario, la emisión de códigos, la whitelist de clientes y de redirect_uri, el canje válido y todos los rechazos: código reutilizado, expirado, de otro cliente e inexistente. También comprueba que el código en claro no queda en la base de datos.

La prueba de extremo a extremo, con los tres servicios levantados, es esta:

  1. GET :8001/tasks sin sesión responde 302 a /sso/start, que a su vez redirige a :8000/authorize?client=task&redirect_uri=....
  2. Sin sesión en el IdP, el authorize responde 302 a /login?client=task&redirect_uri=....
  3. Un login correcto responde 302 a :8001/sso/callback?code=...; el callback canjea y responde 302 a /tasks, que devuelve 200.
  4. En el mismo navegador, GET :8002/facturas devuelve 200 sin formulario: el IdP ya tenía sesión.
  5. POST :8002/logout redirige al /logout del IdP, que destruye la sesión y devuelve al servicio; un request posterior vuelve a pasar por el login.

11. Limitaciones honestas

LimitaciónQué implicaría resolverla
Single logout no federado Front-channel o back-channel logout de OIDC: avisar a cada RP en vez de esperar a su siguiente request.
Sin state, nonce ni PKCE Protección contra CSRF en el callback y contra intercepción del código en clientes públicos.
Whitelist en configuración Registro de clientes en base de datos, con scopes, secretos y rotación.
Sin refresh tokens Renovación de la sesión del RP sin volver a pasar por el IdP.
Sin revocación global Tabla de sesiones SSO y un endpoint que invalide todas las sesiones de un usuario.

Ninguna de estas limitaciones invalida el objetivo del capítulo. El objetivo era demostrar dónde debe vivir la identidad y cómo se coordina entre servicios sin compartir base de datos ni credenciales. Eso está implementado, probado y verificado de punta a punta. Lo que falta es el grosor de un estándar completo, y ese grosor tiene nombre: OIDC.

12. Cómo viaja la cookie y qué sesión manda

Hay un matiz que suele confundirse al seguir el flujo con las herramientas del navegador. Cuando SsoController@authorize ejecuta Auth::check(), no está consultando la sesión de task ni la de billing: está consultando la sesión del IdP. Ese detalle explica por qué el segundo servicio no necesita recibir nada del primero.

La sesión del IdP se crea cuando el usuario envía el formulario de login en :8000: Auth::attempt() escribe la clave login_web_<hash> en la sesión y regenerate() renueva el identificador. El guard web (driver session, definido en user-service/config/auth.php) es el que lee esa clave. La sesión de task —task-service-session, con su api_token— no participa en esa comprobación.

Por eso, cuando el navegador llega a :8000/authorize?client=billing&... después de haber iniciado sesión desde task, Auth::check() ya es true: el IdP reconoce al usuario y emite un código nuevo, esta vez para billing. No reutiliza el código de task; el ticket anterior ya se consumió.

ComponenteQué guardaDónde
IdP Hash del código SSO sso_tickets.code_hash
IdP Sesión del usuario (login) cookie user-service-session
task Su propio token (task-sso) cookie task-service-session → api_token
billing Su propio token (billing-sso) cookie billing-service-session → api_token

La cookie no la transporta código PHP de un servicio a otro: la transporta el navegador. El recorrido es siempre el mismo:

  1. El POST /login responde con Set-Cookie: user-service-session=.... El valor es el identificador de sesión cifrado, no los datos del usuario; los datos quedan en storage/framework/sessions/ porque SESSION_DRIVER=file.
  2. El navegador almacena la cookie por host + path + nombre, sin distinguir puertos. Por eso la envía también a :8001 y :8002, aunque solo el IdP la usa.
  3. Los 302 del flujo hacen que el navegador vuelva a visitar el IdP y adjunte automáticamente la cookie. No hay ningún traspaso manual.
  4. En cada request, el grupo web ejecuta EncryptCookies (descifra con el APP_KEY local) y StartSession (carga la sesión desde el identificador). Como cada servicio tiene un APP_KEY distinto, ninguno puede leer la cookie de otro aunque la reciba.

El nombre y los atributos se definen en user-service/config/session.php: cookie en la línea 130 (Str::slug(APP_NAME).'-session'), path en la 146, domain en la 159 (null, cookie de host), http_only en la 185 y same_site en la 202 (lax). En local, secure queda desactivado porque se sirve por HTTP.

El mecanismo falla en tres casos previsibles: si el usuario se autenticó con POST /api/tokens (los clientes no-navegador no crean sesión web en el IdP), si se alterna entre localhost y 127.0.0.1 (son hosts distintos para el navegador), o si la sesión expiró o se cerró. En los tres, authorize vuelve a pedir login.

La conclusión es la misma que sostiene todo el capítulo: task y billing no se pasan un token; cada uno redirige al IdP, que ya tiene la sesión del usuario, y regresa con su propio token.
