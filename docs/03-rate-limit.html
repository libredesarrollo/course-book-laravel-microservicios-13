Rate limiting en el login: el antes y el después

Resumen: el user-service exponía POST /api/tokens sin ninguna protección. Medido: 8 439 intentos de contraseña por minuto, las 24 horas del día. Este documento recoge qué había antes, qué se añadió después, por qué son dos límites y no uno, y los tres errores que aparecieron al implementarlo.

Contexto: es el endpoint que recibe contraseñas. No es un forgot-password cualquiera — es la puerta de entrada al sistema de identidad, y por lo tanto el objetivo natural de cualquier intento de fuerza bruta.

1. El estado anterior

La ruta era exactamente esto:

<?php

// Público: emitir tokens.
Route::post('/tokens', [AuthController::class, 'store']);

Sin middleware. El controlador hacía su trabajo y ya:

public function store(Request $request): JsonResponse
{
    $validated = $request->validate([
        'email' => ['required', 'email'],
        'password' => ['required', 'string'],
        'device_name' => ['sometimes', 'string', 'max:100'],
    ]);

    $user = User::query()->where('email', $validated['email'])->first();

    if (! $user || ! $user->passwordMatches($validated['password'])) {
        return response()->json(['error' => 'Credenciales inválidas'], 401);
    }

    $issued = ApiToken::issueFor($user, $validated['device_name'] ?? 'api-token');

    return response()->json([
        'token' => $issued['token'],
        'token_type' => 'Bearer',
        'user' => $user,
    ], 201);
}

Y el token se emitía sin caducidad:

public static function issueFor(User $user, string $name = 'api-token'): array
{
    $plain = bin2hex(random_bytes(32));

    $model = $user->tokens()->create([
        'token_hash' => hash('sha256', $plain),
        'name' => $name,
    ]);

    return ['token' => $plain, 'model' => $model];
}

Con la columna definida así:

$table->timestamp('expires_at')->nullable();

Las tres carencias

Estado anteriorRiesgo
Sin rate limit El endpoint aceptaba intentos ilimitados Fuerza bruta contra contraseñas. El más grave de los tres.
Token sin caducidad expires_at nullable y sin valor por defecto Un token robado servía para siempre. No había forma de invalidarlo salvo borrarlo a mano.
Sin registro Un 401 no dejaba rastro Una fuerza bruta era completamente silenciosa. Nadie se enteraba hasta que un usuario perdía su cuenta.

El detalle que lo hizo más grave: el login de la interfaz web sí tenía throttle:6,1. El mismo endpoint, llamado por API, no tenía nada. El límite estaba puesto en el sitio equivocado: protegía el formulario, no la operación.

2. La medición que lo destapó

Cincuenta intentos con contraseña incorrecta, medidos contra el servidor de verdad:

$ for i in $(seq 1 50); do
    curl -s -o /dev/null -X POST http://127.0.0.1:8000/api/tokens \
      -H "Content-Type: application/json" -H "Accept: application/json" \
      -d '{"email":"ana.torres@example.com","password":"intento'$i'"}'
  done

  50 intentos fallidos en 0.4 s -> 8439 req/min sin ninguna proteccion

Un atacante con una conexión decente multiplica esa cifra por cien sin esfuerzo. Y como la base de datos de usuarios es SQLite con dos filas, el cuello de botella lo pone el proceso, no el almacenamiento: a escala real el número sería mayor.

La lección del método: no hubo que leer el código para saber que faltaba algo. Bastó con pedir lo que un atacante pediría y medirlo. Un rate limit que no has probado no existe.

4. La configuración

TodoSale de un archivo, config/tokens.php:

<?php

return [

    'ttl_minutes' => (int) env('TOKEN_TTL_MINUTES', 60),

    'throttle' => [
        'per_account' => (int) env('LOGIN_THROTTLE_PER_ACCOUNT', 5),
        'per_ip' => (int) env('LOGIN_THROTTLE_PER_IP', 20),
        'decay_seconds' => (int) env('LOGIN_THROTTLE_DECAY', 60),
    ],

];

Y en el .env:

# --- Tokens de API -----------------------------------------------------
TOKEN_TTL_MINUTES=60

# Límites de intentos de login sobre POST /api/tokens (recibe contraseñas).
LOGIN_THROTTLE_PER_ACCOUNT=5
LOGIN_THROTTLE_PER_IP=20
LOGIN_THROTTLE_DECAY=60

Por qué un archivo de configuración y no constantes en el código: cambiar un límite de 5 a 20 no debería requerir un deploy. Es una decisión operativa, y las decisiones operativas viven en el entorno.

5. Por qué dos límites y no uno

El limitador se define en AppServiceProvider y devuelve una lista de límites:

RateLimiter::for('login', function (Request $request): array {
    $email = mb_strtolower((string) $request->input('email'));

    return [
        // Una IP puede burnear varias cuentas, pero no una sola
        // cuenta desde muchas IP.
        Limit::perMinute((int) config('tokens.throttle.per_ip'))
            ->by('ip:'.$request->ip()),

        // Y al revés: un atacante con muchas IP contra una sola cuenta.
        Limit::perMinute((int) config('tokens.throttle.per_account'))
            ->by('email:'.hash('sha256', $email).'|ip:'.$request->ip()),
    ];
});

Son dos ataques distintos y cada uno necesita su contador:

AtaqueUn solo límite de 20/min lo frenaría?Qué lo detiene aquí
Una cuenta, una IP
La forma más común		 Sí, pero tardaría 20 intentos El de cuenta corta en 5
Una cuenta, muchas IP
Botnet o proxys rotos		 No. Cada IP tiene su presupuesto y ninguno se agota El de cuenta incluye la IP, así que cambia al cambiar la IP… pero combinado con el de IP, el atacante tampoco puede rotar libremente
Muchas cuentas, una IP
Barrido de emails		 Sí, a los 20 intentos El de IP corta en 20

Laravel aplica el más estricto de los dos. En cuanto uno se agota la respuesta es 429 y el resto también cuentan como consumido, así que agotar uno agota ambos.

Detalle de la clave por cuenta: lleva la IP. Si no, el límite por cuenta se compartiría entre todas las IP, y el atacante solo tendría que rotar IP para no agotarlo nunca.

6. Dónde se aplica

// Público: emitir tokens. throttle:login protege contra fuerza bruta con dos
// contadores (por IP y por cuenta); ver AppServiceProvider.
Route::post('/tokens', [AuthController::class, 'store'])
    ->middleware('throttle:login');

El nombre login es una referencia al limitador registrado con RateLimiter::for('login', ...). Laravel lo busca ahí antes de ejecutar el middleware.

El límite va en la ruta, no en el controlador ni en el middleware global. Solo este endpoint recibe contraseñas. Un throttle global frenaría también la lectura de tareas, que es justo lo que un usuario activo hace sin parar.

7. Caducidad: por qué NOT NULL

La caducidad podría haberse implementado de dos formas. Se eligió la más fuerte:

// Opción A — la habitual: opcional, y confiar en que se rellene
$table->timestamp('expires_at')->nullable();

public static function issueFor(User $user, string $name = 'api-token'): array

// Opción B — la elegida: imposible olvidar la caducidad
$table->timestamp('expires_at');

public static function issueFor(
    User $user,
    string $name,
    DateTimeInterface $expiresAt   // obligatorio, sin valor por defecto
): array

Un token sin caducidad es un token robado que sirve para siempre. Con la opción A, bastaba una llamada a issueFor() sin el tercer argumento y se creaba un token eterno, sin que nada fallara ni avisara.

Con la opción B el error no se puede cometer:

$issued = ApiToken::issueFor(
    $user,
    $validated['device_name'] ?? 'api-token',
    now()->addMinutes((int) config('tokens.ttl_minutes')),
);

Y la consulta de validación se simplifica, porque ya no hay dos casos que tratar:

return static::query()
    ->with('user')
    ->where('token_hash', hash('sha256', $plainToken))
    ->where('expires_at', '>', now())
    ->first();

La opción A tenía además un fallo silencioso que la B elimina: con expires_at nullable, findByPlainText() necesitaba whereNull('expires_at')->orWhere('expires_at', '>', now()). Ese orWhere es exactamente el tipo de condición que se olvida revisar en una refactorización, y su error sería aceptar tokens que deberían haber caducado.

8. Qué se registra y qué no

Cada intento fallido deja un warning:

// storage/logs/laravel.log
Failed login attempt {"email":"ana.torres@example.com","ip":"127.0.0.1","account_exists":true}
Failed login attempt {"email":"nadie@example.com","ip":"127.0.0.1","account_exists":false}

Y también las operaciones que cambian el estado de un token:

API token issued  {"user_id":1,"token_id":4,"device":"curl","expires_at":"2026-10-17T12:14:24+00:00"}
API token revoked {"token_id":4,"user_id":1}

Por qué registrar account_exists

La respuesta al cliente es idéntica en ambos casos ("Credenciales inválidas", 401), y tiene que serlo: si no, el endpoint sirve para enumerar qué emails están dados de alta.

Pero en el log la información sí es útil: un pico de intentos con account_exists: true contra muchos emails distintos es la firma de credential stuffing, y es justo lo que se quiere poder detectar.

Por qué no se registra la contraseña

Nunca. Y no es una convención: hay un test que lo comprueba.

it('never logs the attempted password', function () {
    Log::spy();

    User::factory()->create(['email' => 'ana@example.com']);

    attemptLogin(['password' => 'mi-secreto-muy-largo']);

    Log::shouldHaveReceived('warning')->withArgs(
        fn (string $message, array $context) =>
            ! str_contains(json_encode($context), 'mi-secreto-muy-largo')
    );
});

El riesgo de escribir contraseñas en el log es subestimado. Los logs suelen tener permisos más laxos que la base de datos, se copian a agregadores de terceros, y se conservan meses. Un log de autenticaciones es material de credential stuffing listo para usar.

10. Tres errores al implementarlo

Los tests aparecieron durante la implementación, no después.

10.1 Dos tests que afirmaban lo contrario del código

El primero contaba un token después de un intento fallido:

$this->assertSame(1, ApiToken::query()->count());

El valor correcto era 0: un intento fallido no emite ningún token. El test pasaba a dar falso positivo sobre lo que pretendía medir.

El segundo pedía 401 para un token sin caducidad y recibía 200, porque whereNull('expires_at') lo aceptaba. Ese fallo no era del test: era la evidencia de que la columna nullable estaba permitiendo el token eterno. De ahí salió la decisión de pasarla a NOT NULL.

10.2 expires_at sin castear a datetime

Call to a member function diffInMinutes() on string

Eloquent devuelve las columnas de fecha como string si no hay cast declarado, y solo castea automáticamente created_at y updated_at. Faltaba:

protected function casts(): array
{
    return [
        'expires_at' => 'datetime',
        'last_used_at' => 'datetime',
    ];
}

Sin ese cast, isExpired() habría fallado en producción con "Call to a member function isPast() on string". El error apareció en un test; el lugar donde se habría descubierto en producción es el peor posible.

10.3 Un límite verificado mal

La primera medición "aislamiento por IP" se hizo con X-Forwarded-For esperando ver dos presupuestos. Devolvió 429 en los dos casos, y la conclusión automática —"las IPs no se aislan"— era falsa: la cabecera se estaba ignorando. Las IPs de verdad no se pueden simular desde localhost, así que la demostración correcta es la de los tests, con REMOTE_ADDR distinto.

Un dato que no encaja significa que el test está mal, no que el código esté bien. Cuando la primera medición de seguridad no cuadra, lo sospechoso es el método.

11. La trampa de los proxies

El límite por IP usa $request->ip(). En Laravel eso devuelve la dirección del cliente solo si el proxy de delante está declarado como confiable. Sin configurarlo:

$ curl -H "X-Forwarded-For: 203.0.113.9" -X POST .../api/tokens ...
  401     # la cabecera se ignoró: contó como 127.0.0.1 otra vez

La consecuencia en producción es seria y silenciosa: si la aplicación corre detrás de un balanceador o un ingress, todas las peticiones llegan con la misma IP de proxy, y el límite por IP se convierte en un límite global compartido. En un sistema con muchos usuarios, cinco intentos de login en todo el sistema bloquean a todos.

// bootstrap/app.php
$middleware->trustProxies(at: '*');   // solo si hay un proxy real delante

No se activó en este proyecto a propósito: rompería el aislamiento de los tests y no hay proxy en local. Pero es el primer paso antes de desplegar, y conviene dejarlo anotado junto al límite, no descubrirlo en producción.

12. Cobertura de tests

Doce tests solo para este cambio, en tests/Feature/LoginThrottleTest.php:

Suite completa tras el cambio: user-service 28 tests / 102 asserts y task-service 34 tests / 88 asserts, los dos en verde.

13. Lo que queda abierto

  • Sin refresh tokens. Cuando el token caduca, el usuario vuelve a escribir su contraseña. Aceptable en local, incómodo en una app real. El sitio está previsto: POST /api/tokens/refresh, exchanging el token caducado por uno nuevo.
  • Sin límite global de peticiones. Ahora solo se protege el login. Un atacante podría hammering GET /api/user sin consecuencias.
  • Sin bloqueo de cuenta. El rate limit frena el ritmo, pero no invalida la cuenta. En muchos sistemas eso es justo lo que se quiere: un atacante lento no se ve afectado.
  • Sin aviso al usuario legítimo. Si alguien se equivoca cinco veces, la respuesta 429 es correcta pero la interfaz no explica qué ha pasado ni cuánto falta.
  • Los contadores viven en caché de ficheros. Con CACHE_STORE=file el límite es por instancia. Con varias réplicas, el atacante dispone de N presupuestos. En producción, caché compartida (Redis).

La última es la más importante de la lista. Un rate limit en memoria local solo protege cuando hay una sola instancia. Es el error que hace que un sistema en producción crea estar protegido y no lo esté.

Nota: los límites por cuenta e IP están definidos en AppServiceProvider::registerLoginRateLimiter(), la configuración en config/tokens.php, y el registro de intentos en AuthController::logFailedAttempt(). Los tres están en el user-service porque es el único que recibe contraseñas: el task-service no tiene ni usuario ni token que proteger.
