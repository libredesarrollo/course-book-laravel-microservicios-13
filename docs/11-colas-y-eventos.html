Colas y eventos: el outbox, el webhook firmado y la idempotencia

Capítulo de la serie de microservicios. Hasta b0.7 la comunicación entre servicios era 100% síncrona: cada request crítico pagaba su salto de red. Este capítulo introduce asincronía con colas locales de database y el patrón outbox: el evento task.completed nace en la misma transacción que la tarea, un despachador lo entrega por webhook firmado con HMAC (con reintentos y backoff), billing responde 202 y la factura se crea en su cola. Y como el reparto es at-least-once, el receptor carga con la idempotencia.

El problema: dos servicios que no se conocían

Hasta aquí, task-service y billing-service ni se hablaban. La frase "billing le factura al usuario por cada tarea completada" no existía en el sistema: billing tenía facturas quemadas a mano en un array PHP, sin tabla, y task-service nunca cruzó la frontera proactivamente — solo respondía requests. Y el mail de "tarea completada" corría pegado al request del usuario.

Tres necesidades distintas, mismo capítulo:

NecesidadInstrumentoQuién decide
El mail no debe retrasar la respuesta del usuarioCola database + job SendTaskCompletedEmailtask-service
Billing caído, y el usuario igual completó su tareaOutbox + webhook con reintentostask-service dice a quién entregar: config events.subscribers
El evento puede llegar dos veces; la factura no se puede duplicarUNIQUE en invoices.event_id + cache anti-replaybilling-service

El principio: escribir antes, cruzar después

El antipatrón tentador:

// Mal: la tarea vive, el evento no.
DB::transaction(function () use ($task) {
    $task->update(['status' => 'completed']);
});

Http::post('http://127.0.0.1:8002/api/events', [...]);   // aquí puede morir la historia

Si el Http::post muere (billing caído, timeout, 500), el evento nunca cruzó: la tarea quedó a media historia. Llevarlo a una cola no resuelve la raíz: el mensaje puede perderse entre el commit y la cola.

El patrón outbox invierte el orden. El evento nace dentro de la misma transacción, como una fila normal de la base de datos local — porque es negocio propio:

// task-service/app/Services/TaskCompletion.php (b0.9)
DB::transaction(function () use ($task, $actor, $traceId) {
    $task->update(['status' => 'completed']);

    // Misma transacción: si la tarea no sobrevive, el evento tampoco.
    OutboxEvent::record('task.completed', [
        'task_id' => $task->id,
        'task_title' => $task->title,
        'user_id' => $task->user_id,
        'actor' => $actor,
    ], $traceId);
});

// La red va DESPUÉS, con la fila esperando:
SendTaskCompletedEmail::dispatch($task->fresh(), $actor)->onQueue('mails');

Transacción confirmada = evento garantizado en tierra de origen. La red arranca después, con una fila en el outbox esperando; el despachador la cruza. Tarde, no nunca.

El paquete demo/microservices-events

La regla de la serie: la frontera es código compartido empaquetado. Y igual que en b0.5, mecanismo sin política: el paquete sabe firmar, reintentar y marcar como fallado; no sabe qué es task.completed ni que billing existe — eso vive en el config/events.php de cada aplicación.

Las dos tablas del outbox

outbox_events:     id, event_id UNIQUE, type, payload, trace_id,
                   occurred_at, available_at
outbox_deliveries: outbox_event_id → outbox_events ON DELETE CASCADE,
                   subscriber,    UNIQUE(event_id, subscriber),
                   status pending|delivered|failed, attempts, last_error,
                   available_at, delivered_at

Una fila de entrega por (evento, subscriptor): es el registro de con quién cruza y de los intentos que costó. available_at futuro significa "esperando el backoff", no perdida.

El despachador

El comando corre bajo el scheduler cada minuto (withoutOverlapping):

// task-service/routes/console.php
Schedule::command(DispatchOutbox::class)->everyMinute()->withoutOverlapping();

y su núcleo recorre los eventos pendientes:

// packages/microservices-events/src/Outbox/OutboxDispatcher.php
$events = OutboxEvent::query()
    ->where('available_at', '<=', now())
    ->orderBy('occurred_at')
    ->limit($limit)
    ->with('deliveries')
    ->get();

foreach ($events as $event) {
    foreach ($this->subscribersFor($event->type) as $name => $subscriber) {
        // firstOrCreate: no hay dos intentos en pie para (evento, receptor).
        $delivery = OutboxDelivery::firstOrCreate([
            'outbox_event_id' => $event->id,
            'subscriber' => $name,
        ]);

        if ($delivery->delivered()) { continue; }   // ya cruzó
        if ($delivery->failed()) { continue; }      // agotado su cuota
        if ($delivery->available_at?->isFuture()) { continue; }  // en backoff

        $this->deliverTo($event, $name, $subscriber, $delivery);
    }
}

La entrega: firma y clasificación de los fallos

El cuerpo exacto que se manda es el mismo que se firma. Una conexión rechazada no se confunde con un 5xx del receptor: ambas anotan su last_error y vuelven por el backoff, y ninguna aborta el resto de entregas:

// packages/microservices-events/src/Outbox/OutboxDispatcher.php
private function deliverTo(OutboxEvent $event, string $name, array $subscriber, OutboxDelivery $delivery): bool
{
    $delivery->forceFill(['attempts' => $delivery->attempts + 1])->save();

    $body = (string) json_encode($this->manifest($event));
    $signature = Signature::sign($body, (string) $subscriber['secret']);

    try {
        $response = Http::withHeaders([
            'X-Event-Signature' => $signature,
            'X-Event-Id' => $event->event_id,
            'X-Event-Type' => $event->type,
            'X-Event-Timestamp' => (string) now()->getTimestamp(),
            'X-Request-Id' => $event->trace_id ?? '',
        ])
            ->acceptJson()
            ->timeout((int) config('events.timeout', 3))
            ->withBody($body, 'application/json')
            ->post((string) $subscriber['url']);
    } catch (ConnectionException $exception) {
        $this->recordFailure($delivery, $name, $event, 'Conexión fallida');

        return false;
    }

    if ($response->successful()) {
        $delivery->forceFill(['status' => 'delivered', 'delivered_at' => now()])->save();

        return true;
    }

    $this->recordFailure($delivery, $name, $event,
        'HTTP '.$response->status().': '.substr($response->body() ?? '', 0, 256));

    return false;
}

private function recordFailure(...): void
{
    // backoff [10, 30, 120] (el último se repite) y al agotar
    // max_attempts (5): status 'failed' con su Log::error.
    // Cada entrega lleva su propio reloj y su propia vida.
}

La firma

HMAC SHA-256 con hash_equals del lado receptor — la verificación en tiempo constante elimina los ataques de timing sobre la comparación:

// packages/microservices-events/src/Outbox/Signature.php
public static function sign(string $body, string $secret): string
{
    return hash_hmac('sha256', $body, $secret);
}

public static function verify(string $body, string $signature, string $secret): bool
{
    $known = self::sign($body, $secret);

    return is_string($signature) && hash_equals($known, $signature);
}

En task-service: emitir en la misma transacción

El lugar que marca tareas completadas ya era único (b0.4: TaskCompletion). b0.9 le añade la emisión del evento en la misma transacción y el mail desacoplado en cola:

// task-service/app/Services/TaskCompletion.php
public function complete(Task $task, array $actor, array $attributes, ?string $traceId): Task
{
    $completed = DB::transaction(function () use ($task, $attributes, $actor, $traceId) {
        if ($task->status !== Task::STATUS_COMPLETED) {
            $task->update($attributes);   // título extra si viene en el mismo PUT

            OutboxEvent::record('task.completed', [
                'task_id' => $task->id,
                'task_title' => $task->title,
                'user_id' => $task->user_id,
                'actor' => $actor,
            ], $traceId);
        }

        return $task->fresh();
    });

    // El mail va en cola, fuera de la transacción: no participa del commit.
    SendTaskCompletedEmail::dispatch($completed, $actor)->onQueue('mails');

    return $completed;
}

Nota de política: el evento se emite solo en la transición (pending → completed). Un PUT repetido sobre una tarea ya completa no crea un segundo evento — el outbox no es un boletín de spam. El trace_id viene del X-Request-Id del middleware de observabilidad (b0.3) y viaja luego como X-Request-Id en el webhook: la traza cruza los servicios.

El mail, también en cola

El 200 del usuario no espera al SMTP:

// task-service/app/Jobs/SendTaskCompletedEmail.php
class SendTaskCompletedEmail implements ShouldQueue
{
    public int $tries = 3;
    public array $backoff = [5, 15];

    public function __construct(public readonly Task $task, public readonly array $actor) {}

    public function handle(): void
    {
        Mail::to($this->actor['email'])->send(new TaskCompletedMail($this->task, $this->actor));
    }
}

Detallazo del capítulo: el TaskCompletedMail implementaba ShouldQueue, y con Mail::send() dentro de un job, el framework re-encolaba el Mailable — pero a la cola default, fuera de la política. La unidad de la cola es el servicio; el Mailable se envía en línea dentro del job.

En billing-service: recibir firmado, obrar en cola

El middleware de verificación

Empieza rechazando barato y en orden: primero la configuración del receptor (un 500 sin HTTP de por medio), después firma, frescura y anti-replay:

// packages/microservices-events/src/Http/VerifyEventSignature.php
public function handle(Request $request, Closure $next): Response
{
    $secret = (string) config('events.secret');

    if ($secret === '') {
        logger()->warning('VerifyEventSignature: el receptor no configuró events.secret');

        return response()->json(['error' => 'Receptor no configurado'], 500);
    }

    $signature = (string) $request->header(Signature::HEADER);
    $timestamp = (int) $request->header(Signature::HEADER_TIMESTAMP, '0');
    $eventId   = (string) $request->header(Signature::HEADER_EVENT_ID);
    $type      = (string) $request->header(Signature::HEADER_TYPE);

    if ($this->tooOld($timestamp)) {
        return response()->json(['error' => 'Evento fuera de la ventana de frescura'], 401);
    }

    if (! Signature::verify($request->getContent(), $secret, $signature)) {
        return response()->json(['error' => 'Firma de evento inválida'], 401);
    }

    if ($this->alreadySeen($eventId)) {
        // El emisor es at-least-once; esta re-entrega ya la procesamos.
        // Responder 200 evita que el dispatcher la cuente como fallo.
        return response()->json([
            'received' => true,
            'event_id' => $eventId,
            'status' => 'duplicate',
        ], 200);
    }

    $envelope = $request->json()->all();

    $request->attributes->set('event_id', $eventId);
    $request->attributes->set('event_type', $type);
    $request->attributes->set('event_envelope', $envelope);
    $request->attributes->set('event_payload', (array) ($envelope['payload'] ?? []));

    return $next($request);
}

private function tooOld(int $timestamp): bool
{
    if ($timestamp <= 0) {
        return true;    // sin header fresco: fuera
    }

    $maxAge = max(60, (int) config('events.max_age', 120));

    return abs(now()->getTimestamp() - $timestamp) > $maxAge;
}

private function alreadySeen(string $eventId): bool
{
    // Cache::add es atómico: devuelve true solo la PRIMERA vez; las
    // re-entregas concurrentes obtienen false. La ventana antireplay es
    // 2x el max_age para cubrir más que la de los headers.
    return ! Cache::add(
        self::CACHE_PREFIX.$eventId,               // microservices-events.seen.{id}
        now()->toIso8601String(),
        now()->addSeconds(max(60, (int) config('events.max_age', 120)) * 2),
    );
}

El receptor: el controlador decide

El endpoint responde 202 al instante y encola el trabajo pesado — el 202 es el código del contrato asincrónico:

// billing-service/app/Http/Controllers/Api/EventController.php
public function __invoke(Request $request)
{
    $envelope = $request->attributes->get('event_envelope');

    if ($request->attributes->get('event_type') !== 'task.completed') {
        return response()->noContent();   // 204: recibido, no para mí
    }

    CreateInvoiceFromEvent::dispatch(
        $request->attributes->get('event_id'),
        $request->attributes->get('event_payload'),
    )->onQueue('invoices');

    return response()->json([
        'received' => true,
        'event_id' => $request->attributes->get('event_id'),
    ], 202);
}

El job: la política de billing

Tres reglas del job: el evento que no trae user_id usable se registra y no factura; el evento repetido sale por el exists; y la carrera real entre dos workers la frena el UNIQUE:

// billing-service/app/Jobs/CreateInvoiceFromEvent.php
public function handle(): void
{
    if (! $this->hasValidActor()) {
        Log::warning('Evento sin actor utilizable, no factura', [
            'event_id' => $this->eventId,
        ]);

        return;
    }

    if (Invoice::query()->where('event_id', $this->eventId)->exists()) {
        Log::info('Evento ya facturado (idempotente por event_id)', [
            'event_id' => $this->eventId,
        ]);

        return;   // at-least-once: segunda vez es camino feliz
    }

    try {
        Invoice::create([
            'user_id' => (int) $this->payload['user_id'],
            'event_id' => $this->eventId,          // UNIQUE
            'task_id' => $this->payload['task_id'],
            'task_title' => (string) $this->payload['task_title'],
            'amount' => (float) config('events.charge_per_task', 10.00),
        ]);
    } catch (UniqueConstraintViolationException) {
        // Carrera perdida contra otra corrida del job: la factura ya
        // existe. No es un error; es la garantía mostrando el múculo.
        Log::info('Duplicación impedida por UNIQUE', ['event_id' => $this->eventId]);
    }
}

Las dos líneas de la idempotencia

LíneaInstrumentoQué resuelve
Primera: cache anti-replayCache::add() atómico por event_id en el middlewareLa re-entrega dentro de la ventana devuelve 200 duplicate sin encolar jobs ni tocar tablas
Última: UNIQUE en el dominioinvoices.event_id UNIQUE + catch de UniqueConstraintViolationExceptionLa duplicidad real cuando el cache se evapora (driver array + deploy): la segunda factura nace imposible, sea quien sea el worker

Principio de arquitectura: la garantía no vive en el webhook, vive en el dominio (una columna UNIQUE). Los middlewares y caches son aceleradores y cortocircuitos; el constraint en la tabla es la regla.

Verificación real con los tres servicios

Con los tres servicios levantados, login JWT real de Ana, workers locales (queue:work --queue=mails / --queue=invoices) y un kill -9 en medio:

Receptor (billing-service/.env):

Y en routes/console.php del productor el scheduler; en cada aplicación puede afinar timeout, max_attempts, backoff y max_age en config/events.php.

Elecciones y precios

  • Outbox en la misma BD, no una cola externa. El primer capítulo asincrónico usa colas de database sin broker. El precio: sin scheduler ni workers no hay asincronía — y esa es la lección del capítulo, no un bug.
  • Webhook firmado, no un broker, todavía. El webhook es el puente más simple: cero infra nueva. Cuando las cadenas de servicios (task → billing → notificaciones → reportes) se vuelvan grafos, un broker real es una decisión de infraestructura, no de código.
  • La firma cubre el body exacto; los headers van aparte. Firmar el string del JSON evita toda la guerra de "cómo serialicé esto al firmar". Los ids y la frescura viajan en headers, y el receptor los usa para la ventana anti-replay sin deserializar antes de verificar.
  • Reintentos separados por ubicación. Los reintentos de la entrega del webhook (backoff 10/30/120) son del dispatcher; los del job local (tries, backoff) son de cada cola. Un timeout de red no se confunde con un fallo de dominio.
  • La firma no es autenticación de usuario. Autentica al servicio emisor (clave compartida, según config), no a la persona. El user_id del payload es el actor de negocio del evento; los permisos son de la app receptora.
  • El anti-replay es de ventana limitada. Rechaza repetidos dentro de max_age; un replay a los 3 días ya le llegó pasado de frescura — el negocio para esto le pone UNIQUE al elemento, como lo demuestra el último test del receptor.
