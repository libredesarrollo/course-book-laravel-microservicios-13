Autenticación entre microservicios Laravel: flujo completo

Resumen: cuando dos servicios no comparten base de datos, el que quiere proteger un recurso no puede validar por su cuenta quién está llamando. La solución más simple y la más honesta es que le pregunte al servicio dueño de la identidad por HTTP. Este artículo implementa exactamente eso, muestra el código completo, y explica lo que cuesta.

Lo construiremos sobre un proyecto real de dos servicios: user-service (dueño de los usuarios, autenticador) y task-service (dueño de las tareas). Cada uno con su base de datos, sin llaves foráneas cruzadas, hablando solo por HTTP.

1. El problema que resuelve la autenticación

Antes de añadir autenticación, el flujo era "abierto": cualquiera podía crear, editar y borrar cualquier tarea.

$ curl -X POST http://127.0.0.1:8001/api/tasks \
    -H "Content-Type: application/json" \
    -d '{"title":"Tarea maliciosa","user_id":42}'

201 Created   # sin preguntar quién eres

Y más grave: el user_id venía en el cuerpo del request. La validación por HTTP al user-service solo comprobaba que ese usuario existiera, no que quien llamara fuera ese usuario. Cualquiera podía crear una tarea "de Ana Torres" sin ser Ana.

Eso significa que la validación hacía la mitad del trabajo, y la mitad que faltaba era la importante. La autenticación cierra ese hueco: el user_id deja de ser un dato que el cliente afirma y pasa a ser una identidad que el sistema resuelve.

El punto de partida

// ANTES: el cliente dice quién es, y hay que ir a comprobar que existe
$validated = $request->validate(['user_id' => ['required', 'integer']]);

if ($userService->find($validated['user_id']) === null) {
    return response()->json(['error' => 'El usuario no existe en el sistema'], 422);
}

$task = Task::create([
    'title'   => $validated['title'],
    'user_id' => $validated['user_id'],
]);

El bug de fondo: una validación de existencia no es una autorización. La primera responde "¿este id corresponde a alguien?", la segunda responde "¿tienes derecho a actuar en nombre de ese alguien?". Son preguntas distintas y esta implementación solo hacía la primera.

2. La decisión: validar por HTTP o token stateless

El task-service necesita saber quién llama. Pero la tabla de usuarios y de tokens vive en el user-service. Hay dos caminos, y no son equivalentes.

Validar por HTTP (lo que hicimos)Token stateless (JWT)
Dónde se valida El task-service reenvía el token al user-service El task-service verifica la firma en local, sin llamar a nadie
Latencia por request +1 salto de red (~20 ms en local) 0 saltos
Si el user-service cae Nadie puede autenticarse: 503 en todo La API sigue funcionando con normalidad
Revocar un token Trivial: borrar la fila Difícil: el token es válido hasta que expira
Escalado Cada réplica del user-service recibe carga extra Totalmente horizontal

Elegimos validar por HTTP. Es el diseño arquitectónicamente correcto: el estado de identidad tiene un único dueño y nadie lo replica. El costo es explícito y, sobre todo, demostrable en cinco segundos apagando un servicio.

El downside lo conocemos antes de escribir el código: es exactamente lo que un JWT viene a evitar. Lo dejamos así a propósito, y al final del artículo comparamos las tres opciones con sus números.

3. El flujo, paso a paso

  LOGIN (una vez)

  Cliente ──POST /api/tokens──▶ user-service ──▶ SELECT en users
      │         {email,           │                INSERT en api_tokens
      │          password}        │◀── token en claro (una sola vez)
      │◀────── 201 + token ───────┘

  CADA REQUEST POSTERIOR

  Cliente ──GET /api/tasks──▶ task-service ──GET /api/user──▶ user-service
      │                        middleware                       SELECT por
      │                            │                             hash sha256
      │                            │◀──── {id, name, email} ─────┘
      │                            │
      │                            ▼  "¿quién es este token?"
      │                        request->attributes
      │                            │
      │                            ▼
      │                        db_tasks (user_id = identidad, no input)
      │◀───── 200 / 201 / 401 / 403 ─┘
  1. El cliente manda email y contraseña al user-service.
  2. El user-service verifica el hash de la contraseña y emite un token opaco.
  3. El cliente usa ese token como Authorization: Bearer <token>.
  4. El task-service no puede validarlo (no tiene la tabla), así que se lo reenvía al user-service.
  5. El user-service responde quién es. Si el token no existe o expiró, responde 401.
  6. El task-service guarda esa identidad en la petición y sigue.
  7. El user_id sale de ahí. Nunca del cuerpo del request.

4. La tabla api_tokens (solo hashes)

Schema::create('api_tokens', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();

    // Solo se guarda el hash del token. Si alguien lee esta tabla,
    // no puede suplantar a nadie: el token en claro existe una sola
    // vez, en la respuesta del POST /api/tokens.
    $table->string('token_hash', 64)->unique();

    $table->string('name')->default('api-token');
    $table->timestamp('last_used_at')->nullable();
    $table->timestamp('expires_at')->nullable();
    $table->timestamps();
});

Aquí hay una FK, y está bien: es una integridad interna del user-service con su propia tabla. Lo que no existe son FKs cruzadas hacia tareas.

Emitir el token

public static function issueFor(User $user, string $name = 'api-token'): array
{
    $plain = bin2hex(random_bytes(32));

    $model = $user->tokens()->create([
        'token_hash' => hash('sha256', $plain),
        'name' => $name,
    ]);

    return ['token' => $plain, 'model' => $model];
}

Buscar un token

public static function findByPlainText(?string $plainToken): ?self
{
    if ($plainToken === null || $plainToken === '') {
        return null;
    }

    return static::query()
        ->with('user')
        ->where('token_hash', hash('sha256', $plainToken))
        ->where(fn ($query) => $query->whereNull('expires_at')
                                   ->orWhere('expires_at', '>', now()))
        ->first();
}

La consulta es un índice único sobre un hash de 64 caracteres. O sea, O(1) y sin possibility de colisión práctica.

Por qué SHA-256 y no bcrypt/Argon2: porque el token no es una contraseña que alguien pueda escoger. Son 32 bytes de random_bytes, sin espacio de búsqueda que recorrer. El atacante tendría que adivinar el token entero; hashear es solo para que una fuga de la base de datos no sirva. Con una contraseña chosen por el usuario, el ataque de fuerza bruta sí es realista y ahí sí toca Argon2.

5. El middleware del task-service

Este es el corazón del asunto. El task-service recibe un token que no puede validar, así que lo reenvía.

class AuthenticateWithUserService
{
    public function __construct(private readonly UserServiceClient $users) {}

    public function handle(Request $request, Closure $next): Response
    {
        $token = $request->bearerToken()
            ?? ($request->hasSession() ? $request->session()->get('api_token') : null);

        if (! is_string($token) || $token === '') {
            return $this->reject($request);
        }

        $user = $this->users->authenticate($token);

        if ($user === null) {
            // Token caducado o revocado: la sesión web tampoco sirve ya.
            // Ojo: las rutas /api/* no arrancan sesión, así que hay que
            // preguntar antes de tocarla.
            if ($request->hasSession()) {
                $request->session()->forget('api_token');
            }

            return $this->reject($request);
        }

        $request->attributes->set('authenticated_user', AuthenticatedUser::fromArray($user));

        return $next($request);
    }

    private function reject(Request $request): Response
    {
        if ($request->is('api/*') || $request->expectsJson()) {
            return response()->json([
                'error' => 'Unauthenticated.',
                'message' => 'Envía un token válido como: Authorization: Bearer <token>',
            ], 401);
        }

        return redirect()->guest(route('login'));
    }
}

Ese middleware es el API Gateway de facto: decide 401 en JSON para la API y redirección al login para la UI, según quién esté llamando. Un solo lugar, ningún controller tiene que acordarse.

El cliente que hace el reenvío

/**
 * @return array{id: int, name: string, email: string}|null null si el token no es válido
 */
public function authenticate(string $token): ?array
{
    $response = $this->request('/api/user', ['Authorization' => "Bearer {$token}"]);

    // 401 no es un fallo del servicio: es "este token no vale".
    if ($response->status() === 401) {
        return null;
    }

    if ($response->failed()) {
        throw new UserServiceErrorException(
            "El user-service respondió {$response->status()} al validar el token."
        );
    }

    return $response->json();
}

Fíjate en la distinción: 401 significa "identidad inválida" y se traduce a un null. Cualquier otro status es un problema del servicio y se lanza una excepción. Confundir esos dos casos es un bug clásico: termina tratando "tu token venció" como "el servidor se cayó".

6. De dónde sale el user_id, y por qué ya no se valida

Aquí está el cambio de fondo, y conviene mirarlo de cerca porque es la lección del ejercicio.

public function store(StoreTaskRequest $request): JsonResponse
{
    $validated = $request->validated();

    $task = Task::query()->create([
        'title' => $validated['title'],
        'user_id' => $this->user()->id,     // <-- identidad, no input
        'status' => $validated['status'] ?? Task::STATUS_PENDING,
    ]);

    return response()->json($task, 201);
}

Antes, este método llamaba al user-service por HTTP para comprobar que el user_id fuera válido. Esa llamada ya no existe, y no es un descuido: es que se volvió redundante.

El middleware acaba de confirmar por HTTP que ese mismo usuario existe. Preguntarlo otra vez sería pagar la latencia otra vez para obtener la misma respuesta. La validación y la autenticación hacen el mismo trabajo; con autenticación, la validación quedó absorbida.

Y el user_id desapareció del payload de entrada. StoreTaskRequest ya solo valida title y status. Si un cliente manda user_id a propósito, Laravel lo descarta en silencio.

$ curl -X POST .../api/tasks -d '{"title":"Tarea de Ana","user_id":999}'
{"title":"Tarea de Ana","user_id":1, ...}   [201]   # el 999 se ignoró

Y las tareas de otros

protected function findOwnedTask(int $taskId): Task
{
    $task = Task::query()->findOrFail($taskId);

    abort_unless($this->owns($task->user_id), 403, 'Esta tarea no es tuya.');

    return $task;
}

El user_id almacenado sí se sigue usando, pero para algo distinto: para comprobar propiedad, no para validar identidad. Esa distinción es el corazón del cambio.

7. La UI: sesión web con token

La web no usa cookies de sesión para la identidad, porque no tiene usuarios. Guarda el token del user-service en su propia sesión de Laravel y el middleware lo lee de ahí.

public function store(Request $request, UserServiceClient $users): RedirectResponse
{
    $validated = $request->validate([
        'email' => ['required', 'email'],
        'password' => ['required', 'string'],
    ]);

    try {
        $token = $users->issueToken($validated + ['device_name' => 'task-service-web']);
    } catch (UserServiceErrorException) {
        return back()->withInput($request->only('email'))
                     ->withErrors(['email' => 'Credenciales inválidas.']);
    }

    $request->session()->regenerate();
    $request->session()->put('api_token', $token);

    return redirect()->intended(route('tasks.index'));
}

El task-service nunca ve una contraseña: solo la reenvía y guarda el token que le devuelven.

Logout que revoca de verdad

public function destroy(Request $request, UserServiceClient $users): RedirectResponse
{
    $token = $request->session()->get('api_token');

    // Revocar en el user-service es lo que lo hace inutilizable de verdad:
    // si solo lo borramos de la sesión, el token sigue vivo en su tabla.
    if (is_string($token) && $token !== '') {
        rescue(fn () => $users->revokeToken($token), report: false);
    }

    $request->session()->forget('api_token');
    $request->session()->invalidate();
    $request->session()->regenerateToken();

    return redirect()->route('login');
}

Muchas implementaciones olvidan el paso del revokeToken, y entonces el "cerrar sesión" solo borra una cookie: el token sigue sirviendo desde curl hasta que expira. Ese es un fallo de seguridad, no una molestia.

Dos fuentes de token, una sola regla: el middleware acepta el header Bearer o la sesión. El código es idéntico para ambos, así que la UI y la API no pueden divergir por accidente. Un token válido presentado en la UI vale lo mismo que en la API, porque la validación ocurre siempre en el user-service.

8. Tres errores reales que aparecieron

Ninguno se detectó leyendo el código: los dos primeros los encontraron los tests, y el tercero, curl.

8.1 Fuga de información por route model binding

La primera versión usaba la resolución implícita de modelos:

public function show(Task $task): JsonResponse   // binding implícito

El test esperaba 401 y recibió 404. La causa es el orden de los middleware: SubstituteBindings se ejecuta antes que el de autenticación, así que la base de datos se consultaba antes de saber quién llamaba.

$ curl /api/tasks/1        # sin token
404 Not Found    # -> "esta tarea no existe"

$ curl /api/tasks/999999    # sin token
404 Not Found    # -> indistinguible, pero...

# con un token de Ana:
$ curl /api/tasks/1        # tarea de Luis
403 Forbidden   # -> "existe, pero no es tuya"

Un anónimo podía distinguir qué ids existen en la base de datos de otra persona solo por el código de respuesta. Eso es una fuga de información, por pequeña que parezca.

La solución: sacar la resolución del modelo del binding y hacerla dentro del controller, después de autenticar. Así un intruso solo ve 401 y nunca tiene la ocasión de preguntar por la existencia de nada.

// routes/api.php sigue igual; cambia la firma del método
public function show(int $task): JsonResponse
{
    return response()->json($this->findOwnedTask($task));
}

8.2 Un 500 en cada request de API

$request->session()->forget('api_token');   // RuntimeException

El grupo de middleware api no arranca sesión. Llamar a ->session() ahí lanza "Session store not set on request", y ese 500 solo aparecía cuando el token era inválido, no cuando faltaba. El camino infeliz, sin cobertura.

if ($request->hasSession()) {
    $request->session()->forget('api_token');
}

8.3 "Token expirado" disfrazado de "servidor caído"

La primera versión del cliente trataba cualquier respuesta no exitosa como error del servicio. Con un token caducado el user-service responde 401 y el cliente lo traducía a "el user-service falló", devolviendo 502 en lugar de 401. El usuario veía "error del servidor" cuando en realidad solo tenía que volver a iniciar sesión.

11. El precio: latencia y disponibilidad

Esta es la parte que conviene medir, no suponer.

SIN autenticación (antes)          CON autenticación por HTTP (ahora)

Cliente ──── 5ms ───▶ task-svc     Cliente ─── 5ms ───▶ task-svc
                                    ──── 20ms ───▶ user-svc
Total ≈ 5 ms                         Total ≈ 25 ms

La cascada de disponibilidad

La disponibilidad del task-service pasa a depender de la del user-service de forma directa. Si el user-service está caído:

  • El login falla (503).
  • La API devuelve 503 en todo, incluso para lecturas.
  • La UI muestra una página de error explaining por qué.

Ese último punto es el que hace el coste visible en lugar de abstracto. Sin esa página, el usuario ve simplemente "el sistema no funciona" y no tiene forma de saber que es el otro servicio.

Y lo que se ganó a cambio

  • El estado de identidad tiene un solo dueño. Nadie lo replica ni lo cachea.
  • Revocar es borrar una fila. Inmediato, sin esperar expiraciones.
  • El user-service puede aplicar sus propias reglas sin avisar a nadie.

12. Las alternativas y cuándo tienen sentido

Token stateless (JWT)

El user-service firma un JWT y el task-service verifica la firma en local, sin llamada de red. Resuelve exactamente el problema del apartado anterior.

A cambio:

  • Revocar se vuelve difícil. Hasta que expira, el token vale, lo borres o no.
  • El payload no es secreto: es base64, no cifrado.
  • El reloj de los servicios puede desincronizarse y romper nbf / exp.
  • Si ya tienes base de datos, la tabla de revocación es una fila más.

Cuándo tiene sentido: cuando hay terceros que deben validar el token sin poder consultar tu base de datos. O cuando el user-service es el cuello de botella real.

mTLS o API Gateway

La respuesta de producción para tráfico interno. El servicio se identifica con un certificado (mTLS) o con un token de servicio emitido por un gateway con client_credentials de OAuth2: vida corta, audiencia específica, revocable.

Ventaja sobre todo lo anterior: separa la identidad del servicio de la identidad del usuario. En el diseño de este artículo, el task-service reenvía el token de una persona en cada request; con mTLS, lo identifica el certificado del servidor y el token del usuario viaja dentro.

EnfoqueLatenciaRevocaciónComplejidadCuándo
Validar por HTTP1 saltoInmediataBajaAprendiendo, 2-3 servicios, monolito modular
JWT0 saltosComplexaMediaMuchos servicios, terceros validando
mTLS / Gateway0 saltos extra*Por rotaciónAltaProducción seria, Kubernetes

* mTLS no añade saltos de red, pero sí handshake TLS y gestión de certificados, que es donde está su coste real.

El orden sensato es empezar por validar por HTTP porque es la opción que te deja ver el problema, y saltar a la siguiente cuando ese problema te esté doliendo. Montar mTLS antes de tener dos servicios es pagar una factura que todavía no te llegó.

13. Limitaciones honestas

  • Sin circuit breaker. Con el user-service caído, cada request espera el timeout completo (3 s) antes de rendirse. Un circuit breaker lo convertiría en un fallo inmediato.
  • Un salto de red en cada request. Multiplicado por latencia alta y concurrencia, es el techo de escalado del diseño.
  • Los tokens no expiran por defecto. La columna expires_at existe y el código la respeta, pero el seeder emite tokens sin caducidad. En producción, un TTL corto con renovación sería lo normal.
  • Sin refresh tokens. El cliente tiene que pedir un token nuevo con la contraseña cuando caduque. Aceptable en local, incómodo en una app real.
  • Sin rate limiting en la emisión. El login de la UI tiene throttle:6,1, pero POST /api/tokens del user-service no lo tiene. Es el endpoint que recibe contraseñas: el primero que debería estar limitado.
  • Una sola identidad. No hay roles ni permisos. Cualquier usuario autenticado puede tocar sus propias tareas, que es lo correcto, pero no hay un modelo de autorización más rico.
  • La migración de usuarios existentes. Añadir la columna de contraseña a una tabla ya poblada no tiene valor por defecto. Aquí se resolvió con migrate:fresh porque no había datos reales.

14. ¿Y si hay un tercer microservicio?

Metamos un tags-service: mismo patrón que tasks, su propia base de datos, hablando con el user-service. La pregunta es si hay que volver a escribir el AuthController de tasks, y qué alternativas existen.

Antes de listar opciones conviene mirar qué es realmente ese AuthController, porque no es lo que parece.

// app/Http/Controllers/AuthController.php  (task-service)
show()    -> pinta un formulario
store()   -> POST /api/tokens al user-service, guarda el token en sesión
destroy() -> DELETE /api/tokens al user-service, borra la sesión

Ese controlador no tiene nada de dominio de tareas. Su trabajo es: "soy un cliente del proveedor de identidad, déjame canjear credenciales por un token". Eso es un rol de OAuth client, no de servicio de tareas.

La observación que ordena el debate: hay dos piezas de naturaleza muy distinta.

  • El middleware (~40 líneas) es la frontera de seguridad. Es pequeño, casi no cambia, y su código es el mismo en cualquier servicio.
  • El AuthController (~60 líneas) es casi todo UX: un formulario, un redirect, un mensaje de error. Es el que se va a duplicar.

La pregunta "¿duplico el AuthController?" en realidad es "¿cuántos sitios dejamos que implementen el baile de OAuth client?"

Opción A — Duplicar el AuthController en cada servicio

Copiar el archivo a tags-service tal cual. Es lo que haría cualquiera por defecto, y no es una mala decisión.

A favor: cada servicio se despliega y se rompe de forma independiente. Cada uno puede tener su propio diseño de login, su idioma, su flujo de "olvidé mi contraseña". Ningún servicio depende del release de otro.

En contra: N copias. Si mañana añades rate limiting al login, o manejas un caso raro de CSRF, tienes que acordarte de los N. El coste no es el tamaño del archivo: es el número de sitios donde puede olvidarse alguien de arreglar un fallo de seguridad.

Cuándo: con dos o tres servicios, y siempre que la diferencia de UX sea real. Este proyecto tiene dos, y por eso la opción A es razonable hoy.

Opción B — Extraer a un paquete Composer compartido

Un paquete local, referenciado con un path repository en el composer.json, que exporta el middleware, el controller base y el cliente HTTP del user-service.

// composer.json de cada servicio
"repositories": [
    { "type": "path", "url": "../packages/auth-bridge" }
],
"require": {
    "acme/auth-bridge": "*"
}

Cada servicio recibe el código y puede extenderlo si necesita. Una sola fuente de verdad, y el bug de seguridad se arregla una vez.

A favor: una copia, versionable con etiquetas de Git, y cada servicio puede ajustar la vista sin romper a los demás.

En contra, y es importante: acopla los ciclos de release. Un error en el paqueterompe los tres servicios a la vez, y cada servicio queda clavado en la versión que le funciona. Además aparece el problema clásico de "este servicio necesita un parche del paquete, y ya hay tres en producción". Es un coste que no se ve hasta el cuarto servicio.

Cuándo: cuando ya tienes más de tres o cuatro servicios del mismo equipo y despliegan juntos. Antes de eso es infraestructura por adelantado.

Opción C — Login centralizado en el user-service

El user-service aloja el formulario, recibe la contraseña, emite el token y devuelve al cliente a la app que lo pidió. El task-service y el tags-service no tienen ningún AuthController: solo el middleware.

Cliente ──▶ /login (en user-service)
              │
              ├─ POST /api/tokens  (allí mismo, sin salir del servicio)
              │
              └─▶ redirige a http://tasks.app.local/tasks  + el token

El argumento fuerte, y es contraintuitivo: esto no añade acoplamiento nuevo. Todos los servicios ya dependen del user-service para validar cualquier request, así que movedr el login allí no crea ninguna dependencia que antes no existiera. Lo que hace es eliminar código duplicado.

A favor: una sola UX de login en toda la organización. Y cuando llegue MFA, passkeys o "login con Google", se implementa una vez y todos los servicios lo heredan sin tocar una línea.

En contra: el user-service deja de ser solo un servicio de datos y se convierte en algo con cara de aplicación. Y aparece un problema serio de transporte, que es el siguiente punto.

El detalle que se cuela aquí: cómo cruza el token

El token tiene que volver del user-service al task-service de alguna manera, y cada opción tiene un problema distinto:

MétodoCómo funcionaRiesgo
Query string
?token=...		 El redirect más simple El token queda en los logs del servidor, en el historial del navegador y en la cabecera Referer de la siguiente página. No usarlo.
Fragment
#token=...		 La parte tras el # nunca viaja al servidor Requiere JavaScript para leerlo y guardarlo. Funciona, pero mete JS en el camino crítico del login.
Cookie de dominio padre
.app.local		 El user-service deja la cookie y todos los servicios la leen Exige que las apps compartan dominio padre. Y en realidad, ¿para qué volver al login si la cookie ya autentica a todas?
form_post
(estándar OIDC)		 El user-service devuelve un formulario auto-enviado por POST Es el más correcto para el flujo servidor-a-servidor, y el más inusual de montar.

La observación: en cuanto pensas en cómo transporting el token entre servicios, descubres que la opción C empuja el problema hacia una respuesta más interesante, y por eso termina siendo la opción D.

Opción D — API Gateway / BFF en el borde

Un componente delante de todos los servicios hace el login una vez y entrega a cada servicio una identidad ya resuelta en una cabecera. Los servicios dejan de hablar de autenticación por completo.

Cliente ──▶ Gateway ──X-Authenticated-User: {"id":1,...}──▶ task-service
                │
                ├─▶ tags-service
                └─▶ user-service

Los servicios ya NO llaman al user-service en cada request.

A favor: elimina el salto de red por request (el problema de la sección 11, resuelto de raíz), la política queda en un solo sitio, y añadir un servicio nuevo no requiere tocar auth en absoluto.

En contra, y son graves:

  • La cabecera se puede falsificar. Si alguien alcanza task-service saltándose el gateway, puede mandar X-Authenticated-User a mano y ser Ana. La red interna tiene que estar cerrada y verificada, o la cabecera tiene que ir firmada.
  • El gateway pasa a ser infraestructura crítica: si se cae, no entra nadie.
  • Introduce un componente más que operar, con su propio despliegue, sus logs y sus versiones.

Cuándo: en producción con Kubernetes, cuando el número de servicios hace que la latencia por request importe de verdad. No antes.

Opción E — Que el cliente haga el login

Una SPA o app móvil habla solo con el user-service (o el gateway) para autenticarse, guarda el token en su propio almacenamiento, y lo envía en cada request. Ningún servicio tiene formulario de login.

A favor: los servicios quedan sin una línea de código de UI de autenticación. Es el patrón normal en mobile.

En contra: necesitas ese cliente. Y el token vive en el navegador, lo que reabre la discusión entera de XSS vs httpOnly cookie.

Comparación

Opción AuthController por servicio Saltos de red por request Riesgo principal Cuándo
A. Duplicar Sí, N copias 1 Olvidarse de arreglar un fallo en los N sitios 2-3 servicios, UX distintos
B. Paquete No, se hereda 1 Acoplar los ciclos de release 4+ servicios del mismo equipo
C. Login central No 1 El token viaja en la redirección Cuando el login repetido duela
D. Gateway No, ni middleware 0 Cabecera falsificable si la red no está cerrada Producción seria, muchos servicios
E. Cliente No 1 El token en el navegador Si ya hay SPA o app móvil

Qué haría yo aquí

Con task-service y tags-service, seguiría con la opción A, pero con una disciplina mínima que la hace tolerable:

  1. El middleware se mantiene sin cambios: es la frontera de seguridad y debe ser idéntica en todas partes. Si algún día hay que cambiarlo, se cambia en todos a la vez, y los tests de los tres servicios lo cubren.
  2. El UserServiceClient también se mantiene sin cambios, por el mismo motivo.
  3. El AuthController, en cambio, es candidato natural a moverse al user-service (opción C) en cuanto exista una tercera aplicación. No antes: con dos, la duplicación es más barata que el acoplamiento.

El momento exacto del cambio no lo marca el número de servicios, sino una pregunta concreta: "¿cuántas veces al mes me va a doler corregir el login en todos lados a la vez?" Si la respuesta es "una", quédate en A. Si es "varias", ve a C.

El anti-patrón a evitar

Existe una sexta opción que parece sensata y no lo es: convertir el user-service en el dueño de las sesiones de los demás servicios, de forma que task-service y tags-service consulten "quién es el usuario de esta sesión" directamente, sin tokens.

Rota el aislamiento por dentro: el user-service acaba guardando estado de sesión de otras aplicaciones, y cualquier servicio que quiera saber quién es necesita hablar con él de todos modos. Se parece a la opción C pero pierde el control de la sesión, que es justo lo que hace útil al token.

15. Una carpeta con clases reutilizables

La intuición es correcta y es la respuesta que más se repite en equipos que llevan tiempo con microservicios. Pero conviene separar tres cosas que aquí van mezcladas: qué conviene compartir, con qué mecanismo, y cuándo conviene hacerlo.

Esto ya está en el artículo: lo que se propone es la opción B de la sección 14, un paquete Composer local, con el riesgo de acoplar ciclos de release que allí se menciona. Lo que sigue es el detalle fino: qué se comparte, cómo se hereda y cuándo compensa.

15.1 "Una carpeta" tiene tres problemas que no son de estilo

Antes de elegir la herramienta, hay que ver por qué el naive no funciona. Una carpeta compartida entre servicios parece inocente, pero:

  • Git no comparte historia. Si shared/AuthenticateWithUserService.php vive en el repo de task-service y tags-service la importa, Git no sabe que son el mismo archivo. Un git blame no lleva de un servicio al otro, y el historial de un cambio de seguridad no aparece en ninguno de los dos.
  • Un cambio obliga a mover todos. Si es código compartido, entonces está acoplado: tocarlo significa que todos los servicios consumidores cambian de comportamiento en el mismo momento. Eso no es una carpeta, es un despliegue coordinado disfrazado.
  • Nadie sabe qué es "compartido". En la práctica la carpeta crece hasta que contiene el 60% del framework y nadie sabe qué esAPI pública y qué es interno de un servicio.

Ese último punto es el que mata las carpetas compartidas en la práctica. La frontera se diluye sola.

15.2 "Heredar" es el mecanismo equivocado

La pregunta fue si los servicios futuros podrían heredar de los archivos del task-service. Conviene separar dos cosas:

HerenciaComposición
tags-service extends AuthenticateWithUserService Cambias el middleware para los dos a la vez Nadie lo nota
tags-service usa AuthenticateWithUserService Cambias solo un servicio, a propósito El diff lo muestra explícitamente
Cambiar la autenticación a JWT en el futuro Imposible solo en uno Cambias uno, pruebas, decides

El caso del JWT lo deja claro: la sección 12 de este artículo dice que el día que se pase a JWT habrá que cambiar la autenticación. Con herencia no se puede cambiar en un solo servicio sin arrastrar a todos. Con composición, se cambia en uno, se despliega, se mide, y solo después se extiende.

La conclusión no es "nunca heredes", sino: hereda comportamiento, compone decisiones. Una clase base para "toda aplicación web con login" es razonable. Heredar de "la autenticación por HTTP contra el user-service" es casarse con una decisión que explícitamente se dejó abierta para poder cambiarla.

15.3 Lo que de verdad es reutilizable

La pregunta útil no es "¿comparto el middleware?", sino "¿qué lleva dentro cada clase: vocabulario o decisiones?"

Candidato¿Qué lleva dentro?Riesgo de compartirloVeredicto
AuthenticatedUser Solo un DTO: id, name, email Ninguno. Es vocabulario Compartir ya
Chequeo de propiedad (owns(), findOwnedTask()) Un patrón de autorización por dueño Bajo. Casi todos los servicios lo querrán Compartir ya
Contrato de errores (503 / 502) La política de cómo se traduce una caída de red Bajo, y evita respuestas inconsistentes Compartir ya
UserServiceClient URL, timeout, clasificación de errores, y la decisión de validar por HTTP Medio. Es justo lo que se va a cambiar si se pasa a JWT Compartir la interfaz, no la implementación
AuthenticateWithUserService La frontera de seguridad, atada a un proveedor concreto Alto. Es la decisión central del diseño No compartir todavía
AuthController UX: formulario, redirect, mensajes Bajo técnicamente, alto en fricción de despliegue No compartir (ver 15.2)

La regla que sale de esta tabla: comparte el vocabulario, no las decisiones. "Un usuario autenticado es un AuthenticatedUser con id, name y email" es un concepto estable. "Para validar quién es, hay que llamar por HTTP al user-service" es una decisión de arquitectura, y las decisiones se cambian sustituyendo, no heredando.

15.4 Las cinco formas de compartir de verdad

Una vez que se sabe qué se comparte, el mecanismo importa menos de lo que parece:

A. Carpeta copiada a mano

cp ../user-service/app/Support/AuthenticatedUser.php app/Support/
cp ../user-service/app/Http/Middleware/AuthenticateWithUserService.php app/Http/Middleware/

A favor: cero acoplamiento. Cada servicio se despliega y se rompe solo, y es trivial de entender.
En contra: divergencia silenciosa. Si arreglas un fallo de seguridad, los otros se quedan con la versión vieja, y no hay nada que te avise.

B. Paquete Composer con path repository

"repositories": [
    { "type": "path", "url": "../packages/microservice-kit" }
],
"require": {
    "acme/microservice-kit": "*"
}

A favor: una fuente de verdad real, y es la opción más simple de montar sin publicar nada.
En contra, y es lo que más muerde: el "*" significa "instala siempre la última". Un cambio en el paquete aparece en todos los servicios sin cambio de versión, sin commit en cada uno y sin que nadie lo decida. Fijar una etiqueta resuelve eso, y en cuanto la fijas estás haciendo releases: el acoplamiento vuelve por la puerta de atrás.

C. Git submodule

A favor: un commit del submodule apunta a un punto exacto del repositorio compartido, así que la trazabilidad es perfecta.
En contra: la experiencia de desarrollo es mala. Todo el mundo odia trabajar con submodules. Clonar, actualizar, resolver conflictos, y un git status que no dice nada útil. Para código de aplicación es una mala señal.

D. Paquete en un registry privado

A favor: la forma profesional. Versionado semántico real, cada servicio fija la versión que le funciona, y se actualiza cuando el equipo lo decide.
En contra: hay que publicar releases de verdad. Un paquete para tres consumidores, donde uno solo es el que produce el cambio, es mucha ceremonia para poca cobertura.

E. Generar en lugar de compartir

En lugar de una dependencia, una plantilla: un repositorio base, o un comando php artisan make:service-template, que al crear un servicio nuevo le estampa el patrón actual. A partir de ahí, cada servicio es libre y diverge sin culpa.

php artisan make:service tags --template=microservice
# -> crea tags-service con:
#    - UserServiceClient (copia, editable)
#    - AuthenticateWithUserService (copia, editable)
#    - AuthenticatedUser (copia, editable)
#    - AuthController (copia, editable)
#    - tests que ya pasan contra el user-service real

A favor: combina lo mejor de las dos cosas. Los servicios nuevos nacen consistentes y sus tests ya funcionan, pero después no hay ninguna dependencia que los ate. Un cambio en tags-service no rompe a nadie, y el siguiente servicio lo vuelve a coger con la versión mejorada.
En contra: no resuelve el bug de seguridad en los servicios ya existentes. Para eso hace falta lo de la opción B o D, pero solo para el DTO y el contrato de errores, que es donde no hay decisiones.

15.5 La regla de tres

Existe una regla empírica antigua y sigue siendo la mejor guía: no extraigas hasta la tercera copia.

Con task-service y tags-service hay dos. Extraer con dos instancias es prematuro por dos razones: todavía no sabes qué parte es común y cuál es propia de cada servicio, y el coste del mecanismo no se ha justificado con nadie. Cuando llegue el tercero, ya tendrás la respuesta empírica de qué se parece en la realidad, no en tu imaginación.

15.6 El coste invisible: los tests

Hay un efecto secundario que solo se nota después, y merece su propio párrafo. El código compartido sin tests compartidos es peor que el código duplicado con sus tests:

  • Con código duplicado, cada servicio tiene sus tests y su copia. Si rompes algo, lo detectas en ese servicio. El coste es mantener copias.
  • Con código compartido, los tests viajan con el código, pero solo se ejecutan en el CI de quien tiene el paquete. Si un servicio se actualiza a una versión nueva y el otro se queda atrás, cada uno ejecuta tests distintos sobre el mismo código, y ninguno cubre la combinación.

Por eso, si se comparte algo, lo que se comparte tiene que ser el código junto con sus tests, y el CI de cada servicio tiene que correr la suite de ambos. Si eso no es posible, es una señal de que compartir era la decisión equivocada.

15.7 Mi opinión

Con lo que hay hoy: genera, no compartas. Es decir, la opción E para lo que viene, y no extraer todavía nada.

El orden que propongo, en el tiempo:

  1. Ahora (2 servicios): nada. Duplica si hace falta. Que tags-service tenga su propia copia del middleware, y que se llame igual. Las dos van a estar bien durante meses.
  2. Con el tercer servicio: aplica la regla de tres. Mira qué se parece en la realidad y qué no, y entonces decide.
  3. Lo que sí puedes compartir desde ya, y que es gratis: el AuthenticatedUser (un DTO, cero decisiones) y el contrato de errores 503/502 (que además evita respuestas inconsistentes entre servicios). Eso entra en un path repository sin ningún riesgo, porque no contiene ninguna decisión de arquitectura.
  4. Lo que no debes compartir nunca: la decisión de validar por HTTP. Eso vive en cada servicio, y el día que se cambie a JWT o a gateway, se cambia en uno, se despliega, se mide, y solo después se extiende.

Y la regla de oro que resume todo el capítulo: comparta el vocabulario, componga las decisiones.

La trampa de fondo: la sensación de que "compartir código" es sin coste de verdad. Compartir es la manera barata de no volver a escribir, pero paga en no poder cambiar. En un sistema que todavía está cambiando de arquitectura —y este lo está, de HTTP a JWT a gateway— esa es justo la moneda que no quieres gastar.

Nota: la implementación usa tokens opacos generados con random_bytes y almacenados como SHA-256, sin Sanctum ni ninguna dependencia añadida. La validación se hace por HTTP contra el user-service en cada request, de forma deliberada, para poder observar el costo en lugar de teorizarlo.
